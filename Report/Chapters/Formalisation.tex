\section{Formalisation}\label{sec:formalisation}
This section describes the mechanisation of \pill{} in Lean 4, bridging the theoretical foundations developed in~\cref{sec:background,sec:binding-architecture} and their concrete implementation. The formalisation is organised into three top-level namespaces: \texttt{PiLL.Model}, which defines the static structure of the calculus, \texttt{PiLL.Semantics}, which defines its operational behaviour, and \texttt{PiLL.SessionFidelity}, which establishes the metatheoretic results connecting the two. Each component is presented in dependency order, highlighting design decisions and divergences from the presentation of \citet{abs-2106-11818}.

\subsection{Model}\label{subsec:model}
The \texttt{Model} namespace formalizes the static structure of the full \pill{} calculus and is organized around the layered architecture introduced in~\cref{sec:background}. The mechanisation proceeds bottom-up: session types, defined in \texttt{STypes/}, provide the binding structure used by processes in \texttt{Processes/}, processes are then typed relative to environments and hyperenvironments from \texttt{Environments/} and \texttt{HyperEnvironment/}, finally, typing derivations and their metatheoretic infrastructure are collected in \texttt{Judgement/}. This includes inversion lemmas, linearity properties, substitution principles, and the co-finite freshness machinery described in~\cref{subsec:co-finite-quantification}. Shared syntactic infrastructure used across these layers is provided by \texttt{Base.lean}. An overveiw of the file structure can be found in \cref{lst:lean-file-structure}.

\subsubsection{Session Types}\label{subsubsec:stypes}
Session types are defined in \texttt{STypes/Basic.lean} as the inductive datatype \texttt{Types}. Following the locally nameless syntax established in \cref{subsec:locally-nameless}, type variables are isolated into a separate inductive type, \texttt{TVar}, which explicitly distinguishes between free and bound occurrences:

\begin{lstlisting}[language=Lean4]
inductive TVar : Type
  | free  (x : FTVar)   
  | bound (x : BTVar)   
\end{lstlisting}

Here, \texttt{FTVar} represents a free type variable identified by a natural number, while \texttt{BTVar} represents a bound type variable encoded as a De Bruijn index.

The remaining constructors directly mirror the theoretical grammar of the calculus. In addition, the formalisation introduces uninterpreted atomic types (\texttt{atom} and \texttt{atomDual}), representing protocol leaves not further decomposed by the session type grammar and providing the base cases for the inductive structure of the syntax. \Cref{tab:types-comparison} illustrates a representative correspondence between the paper syntax, the locally nameless representation, and the Lean implementation.

\begin{highlight}
\begin{table}[htbp]  
    \centering
    \caption{Comparison of standard, locally nameless, and Lean representations for \pill{} types.}
    \label{tab:types-comparison}
    \begin{tabular}{llll}
        \toprule
        \textbf{Standard} & \textbf{Locally Nameless} & \textbf{Lean Constructor} & \textbf{Binds} \\
        \midrule
        $\thl{A \tensor B}$ & $\thl{A \tensor B}$         & \texttt{| tensor (A B~: Types)} & None \\
        $\thl{1}$           & $\thl{1}$                   & \texttt{| one}                  & None \\
        $\thl{\forall X.A}$ & $\thl{\forall. A}$ & \texttt{| forall\_ (A~: Types)} & 1 type \\
        $\thl{\exists X.A}$ & $\thl{\exists. A}$ & \texttt{| exists\_ (A~: Types)} & 1 type \\
        $\thl{X}$           & $\thl{X}$                   & \texttt{| var (v~: TVar)}       & None \\
        \bottomrule
    \end{tabular}
\end{table}
\end{highlight}

Notably, the polymorphic binders {$\thl{\forall.A}$} and {$\thl{\exists.A}$} reflect the depth-indexed approach detailed in \cref{subsec:co-finite-quantification}. As shown in \cref{app:session-types}, the corresponding Lean constructors keep the bound De Bruijn index implicit, taking only the continuation body \texttt{A} as an argument. An underscore ``\texttt{\_}'' is appended to the constructor names to prevent namespace collisions with Lean's built-in \texttt{forall} and \texttt{exists} keywords.

\paragraph{Duality} \texttt{Types.dual} implements duality as a structurally recursive function, mapping each constructor to its dual. For example:

\begin{lstlisting}[language=Lean4]
def Types.dual : Types -> Types
  | .atom n     => .atomDual n
  | .atomDual n => .atom n
  | .tensor A B  => .parr    (dual A) (dual B)
  | .forall_ A   => .exists_ (dual A)
  | .one         => .bot
  | ...
\end{lstlisting}

The fundamental property that duality is an involution, {$\thl{{(A^\bot)}^\bot = A}$}, is proved in \path{STypes/Lemmas.lean} by structural induction.

The formalisation additionally establishes that duality preserves local closure and commutes with both shifting and substitution:
\begin{highlight}  
\begin{gather*}
\thl{A}.\texttt{lc} \iff \thl{A^\bot}.\texttt{lc} \qquad
\thl{\shiftdc{d}{c}(A^\bot) = {(\shiftdc{d}{c}A)}^\bot} \qquad
\thl{B^\bot\{A/k\}} = \thl{{(B\{A/k\})}^\bot}
\end{gather*}
\end{highlight}

\paragraph{Local closure} \texttt{STypes\slash{}Properties.lean} defines local closure for types as a depth-indexed predicate \texttt{Types.lc (k~: Nat)~: Types $\to$ Prop}, where the depth parameter $k$ tracks how many binders the recursion has traversed. 

At the leaves of the syntax tree, local closure is evaluated by the helper predicate \texttt{TVar.lc}. Because free variables are explicit they do not contain any indices, as such they are inherently locally closed at any depth. By contrast, a bound variable is only locally closed if its De Bruijn index $i$ is strictly less than the current depth $k$, ensuring it points to an enclosing scope:

\begin{lstlisting}[language=Lean4]
def TVar.lc : Nat -> TVar -> Prop
  | _, .free _   => True
  | k, .bound i  => i < k
\end{lstlisting}

The primary \texttt{Types.lc} predicate is then defined by structural recursion. For non-binding constructors, the depth parameter distributes across the sub-terms. When a variable is encountered, the predicate delegates the check to \texttt{TVar.lc}. When descending into the body of a polymorphic binder, the depth counter increments by one, bringing the newly introduced index safely into scope:

\begin{lstlisting}[language=Lean4]
def Types.lc : Nat -> Types -> Prop
  | _, .one         => True
  | k, .var v       => TVar.lc k v
  | k, .tensor A B  => A.lc k /-$\land$-/ B.lc k
  | k, .forall_ A   => A.lc (k + 1)
  | k, .exists_ A   => A.lc (k + 1)
  | ...
\end{lstlisting}

Finally, a type is defined as \emph{closed} if it contains no dangling indices at the top level, meaning it is locally closed at depth $0$. This is registered as the abbreviation \texttt{Types.lc\_0}.

\paragraph{Shifting} \path{STypes/Shift.lean} defines shifting following the standard De Bruijn shifting operation introduced in \cref{subsec:co-finite-quantification}. The operation traverses the syntax tree structurally using a cutoff depth $d$ and a shift amount $c$.

For standard connectives, shifting distributes recursively across subterms, while base constructors such as \texttt{one} and \texttt{bot} remain unchanged. When traversing a polymorphic binder like \texttt{forall\_}, the cutoff depth increments by one to account for the newly entered scope:

\begin{lstlisting}[language=Lean4]
def Types.shift (d c : Nat) : Types -> Types
  | .var v       => .var (v.shift d c)
  | .tensor A B  => .tensor (A.shift d c) (B.shift d c)
  | .forall_ A   => .forall_ (A.shift (d + 1) c)
  | t            => t
\end{lstlisting}

At the variable level, free variables remain unchanged. For bound indices, the function compares the De Bruijn index $i$ against the cutoff depth $d$. Indices satisfying $i < d$ are locally bound within the traversed scope and therefore remain unchanged. Otherwise, the index is incremented by $c$ to preserve its reference to the surrounding environment:

\begin{lstlisting}[language=Lean4]
def TVar.shift (d c : Nat) : TVar -> TVar
  | .bound i => if i < d then .bound i else .bound (i + c)
  | .free n  => .free n
\end{lstlisting}

The operation is exposed through the common \texttt{HasShift} interface, allowing the notation $\shiftdc{d}{c}A$, $A\uparrow{c}$ and $A^+$ to be used uniformly for types and, later, for processes, environments, and hyperenvironments; the shared notation declarations are given in \cref{lst:lean-common-notation}.

\paragraph{Substitution} \path{STypes/Subst.lean} defines substitution as the replacement of a target De Bruijn index $k$ in a host type $B$ by a payload type $A$, denoted $B\{A // k\}$. At the variable level, the function compares a bound De Bruijn index $i$ with the target depth $k$. If $i = k$, the target index has been reached and the variable is replaced by $A$. If $i < k$, the variable is bound by an inner scope and is left unchanged. Finally, if $i > k$, the index refers to an outer binder beyond the substituted variable. Since substitution removes the binder corresponding to $k$, such indices are decremented by one to preserve their relative distance to the surrounding environment.

\begin{lstlisting}[language=Lean4]
def Types.subst (B A : Types) (k : Nat) : Types :=
  match B with
  | .var (.free n)  => .var (.free n)
  | .var (.bound i) =>
      if i == k then A
      else if i > k then .var (.bound (i - 1))
      else .var (.bound i)
  | .tensor A B => .tensor (A.subst A k) (B.subst A k)
\end{lstlisting}

The operation is lifted to the full \texttt{Types} syntax by structural recursion. For ordinary connectives, substitution distributes across subterms. When descending into a polymorphic binder such as \texttt{forall\_}, the target depth is incremented to $k+1$, and the payload type $A$ is shifted by one. This prevents the free indices in $A$ from being captured by the newly entered binder:

\begin{lstlisting}[language=Lean4]
  | .forall_ B => .forall_ (B.subst (shift 0 1 A) (k + 1))
\end{lstlisting}

The interaction between substitution and local closure is captured by \texttt{Types.lc\_subst\_inv}, which states that substituting a type $A$ locally closed at depth $n + k$ for index $k$ in $B$ preserves local closure: $(B\{A / k\}).\texttt{lc}(n+k) \iff B.\texttt{lc}(n+k+1)$. Intuitively, substituting for index $k$ removes one binder from $B$, so local closure at $n+k$ in the substituted term corresponds to local closure at $n+k+1$ in the original. The specialisation \texttt{Types.lc\_subst\_inv\_0} fixes $k = 0$, which is the form later used in the proof of \texttt{Typing\_preserves\_lc}.

As with shifting, substitution is exposed through the common \texttt{HasSubst} interface, allowing the notation $B\{A // k\}$ to be reused when substitution is lifted to processes, environments, and hyperenvironments (see \cref{lst:lean-common-notation}).

\paragraph{Notation} \path{STypes/Notation.lean} introduces notation mirroring the mathematical presentation from \cref{subsec:types}. The only divergence is that exponentials are written {$\thl{\bang\bang A}$} and {$\thl{\query\query A}$} to avoid clashes with Lean syntax. Linear implication $\thl{A \mathbin{\multimap} B}$ is defined as syntactic sugar for $\thl{A^\bot \parr B}$. The corresponding Lean notation declarations are given in \cref{lst:app-lean-type-notation}.

\subsubsection{Processes}\label{subsubsec:processes}
Processes are defined in \path{Processes/Basic.lean} as the inductive type \texttt{Proc}. Following the established locally nameless architecture, channel references are partitioned into a dedicated \texttt{Channel} inductive. Explicit free channels are instantiated as concrete natural numbers (\texttt{FPName}). While the raw process syntax permits arbitrary reuse of these numbers, using \texttt{Nat} allows the formalisation to systematically compute strictly fresh names by incrementing the supremum of any finite set of existing names (mechanised in \path{Processes/Fresh.lean}). Conversely, bound channels are represented using De Bruijn indices, encoding their relative distance to the corresponding binder.

\begin{lstlisting}[language=Lean4]
inductive Channel : Type where
  | free  (x : FPName)
  | bound (x : BPName)
\end{lstlisting}

As discussed in \cref{subsec:locally-nameless}, binding constructs in the process syntax no longer carry explicit payload variables. Instead, bound occurrences are captured purely by their relative position. Comparing the standard paper grammar with the intermediate locally nameless notation and the final constructors of the \texttt{inductive Proc} type illustrates this abstraction:

\begin{highlight}  
\begin{center}
\begin{tabular}{llll}
    \toprule
    \textbf{Standard} & \textbf{Locally Nameless} & \textbf{Lean Constructor} & \textbf{Binds} \\
    \midrule
    $\phl{\send{x}{y}{P}}$ & $\phl{\send{x}{\bullet}{P}}$ & \texttt{| tensor (x~: Channel) (P~: Proc)} & 1 channel \\
    $\phl{\recv{x}{y}{P}}$ & $\phl{\recv{x}{\bullet}{P}}$ & \texttt{| parr (x~: Channel) (P~: Proc)} & 1 channel \\
    $\phl{\res{xy}{P}}$ & $\phl{\res{(\bullet, \bullet)}{P}}$ & \texttt{| cut (P~: Proc)} & 2 channels \\
    $\phl{\recvtype{x}{X}{P}}$& $\phl{x(\diamond).P}$ & \texttt{| input (x~: Channel) (P~: Proc)} & 1 type \\
    $\phl{\clientdup{x}{x'}{P}}$ & $\phl{\clientdup{x}{\bullet}{P}}$ & \texttt{| duplicate (x~: Channel) (P~: Proc)} & 1 channel \\
    \bottomrule
\end{tabular}
\end{center}
\end{highlight} 

Notice that \texttt{cut} takes only a continuation {$\phl{P}$} with no explicit channel arguments, as both dual endpoints are simultaneously bound as indices $0$ and $1$ within the scope of {$\phl{P}$}. Similarly, for constructs like \texttt{tensor}, \texttt{parr}, and \texttt{input}, the subject channel $x$ over which the interaction occurs is kept explicit, while the transmitted payload is anonymized into the continuation. The full inductive definition is listed in \cref{app:processes}. 

\paragraph{Opening and closing} \path{Processes/OpenClose.lean} defines opening and closing operations following the locally nameless principles established in \cref{subsec:opening-and-closing}. In the theoretical presentation, opening a process at depth $k$ with $x$ is denoted as {$\phl{\{k \mapsto x\}P}$}, and conversely, abstracting a specific name back into a bound index is denoted as {$\phl{\{k \mapsfrom x\}P}$}. 

To mechanise this in Lean, we denote explicit free channels as $\#x$ (mapping to \texttt{Channel.free x}) and introduce custom notation for these substitution operations. Expressions such as $\dopen{P}{k | \#x}$ and $\dopen{P}{k | \#x,\#y}$ denote the opening of a process by instantiating the $k$-th (and $k+1$-th) bound indices with free channels. Conversely, $\dclose{P}{k | \#x}$ and $\dclose{P}{k | \#x, \#y}$ denote the closing of a process by abstracting $x$ and $y$ back into De Bruijn indices. For convenience, the depth parameter can be omitted when operating at the innermost binder ($k=0$), simplifying the notation to $\dopen{P}{\#x,\#y}$ and $\dclose{P}{\#x,\#y}$. The typeclasses and notation declarations supporting these overloaded operations are collected in \cref{app:common-notation}.

Because binders are represented positionally, the depth parameter $k$ increments according to the number of channels bound by each constructor. For standard communication prefixes like \texttt{tensor}, \texttt{parr}, and the server \texttt{duplicate} operation, exactly one channel is bound, incrementing $k$ by one. The restriction constructor (\texttt{cut}) simultaneously binds two dual endpoints, requiring $k$ to increment by two. The \texttt{input} constructor binds a type variable rather than a channel and therefore leaves $k$ unchanged. The \texttt{server} constructor additionally carries an explicit set of dependency channels \texttt{zs~: Finset Channel}, representing the replicable processes the server depends on,which must be acted on simultaneously with $x$ and $P$.

\begin{lstlisting}[language=Lean4]
def Proc.open (P : Proc) (u : Channel) (k : Nat) : Proc :=
  match P with
  | .tensor x P     => .tensor (x.open u k) (P.open u (k + 1))  
  | .parr   x P     => .parr   (x.open u k) (P.open u (k + 1))  
  | .cut      P     => .cut                 (P.open u (k + 2))
  | .duplicate x P  => .duplicate (x.open u k) (P.open u (k + 1))
  | .server x zs P  => .server (x.open u k) (zs.open u k) (P.open u k)
  | .input  x P     => .input  (x.open u k) (P.open u k)
  | ...
\end{lstlisting}

For channel occurrences, the recursive traversal delegates to \texttt{Channel.open}, for the dependency set carried by a server, it uses the pointwise lifting \texttt{Finset.open}. For bound channels, the De Bruijn index $i$ is compared against the target depth $k$ and replaced with $v$ upon an exact match. For dependency sets, \texttt{Channel.open} is mapped pointwise. In both cases free channels remain entirely unaffected:

\begin{lstlisting}[language=Lean4]
def Channel.open (u v : Channel) (k : Nat) : Channel :=
  match u with
  | bound i => if i == k then v else bound i

def Finset.open (zs : Finset Channel) (v : Channel) (k : Nat) : Finset Channel :=
  zs.image (fun u => u.open v k)
\end{lstlisting}

For restriction, the two-name opening interface is instantiated by sequential opening, replacing index $k+1$ with the second endpoint $v$, then replacing index $k$ with the first endpoint $u$:

\begin{lstlisting}[language=Lean4]
instance : HasOpenTwo Proc Channel Channel Nat where
  open_ P u v k := (Proc.open (Proc.open P v (k + 1)) u k)
\end{lstlisting}

To complete the bidirectional infrastructure, \texttt{Proc.close}, \texttt{Channel.close}, and \texttt{Finset.close} define the corresponding closing operation. \texttt{Proc.close} traverses the process tree using a structural recursion identical to \texttt{Proc.open}, applying the same depth-incrementing rules. At the leaves, \texttt{Channel.close} compares each free channel against the target name $x$ and abstracts it into a bound De Bruijn index at depth $k$ upon a match, while bound indices are left unchanged. Dependency sets are handled pointwise by \texttt{Finset.close}:

\begin{lstlisting}[language=Lean4]
def Channel.close (u : Channel) (x : FPName) (k : Nat) : Channel :=
  match u with
  | .free name => if x == name then .bound k else .free name
  | .bound i   => .bound i

def Finset.close (zs : Finset Channel) (x : FPName) (k : Nat) : Finset Channel :=
  zs.image (fun u => u.close x k)
\end{lstlisting}

\paragraph{Local closure} \path{Processes/LocalClosure.lean}
defines local closure for processes as a two-parameter predicate \texttt{Proc.lc (k n~: Nat)~: Proc $\to$ Prop}. Because the calculus features a two-sorted syntax, the predicate must maintain independent depth counters: $k$ tracks the depth of channel binders, while $n$ tracks the depth of type binders. The type depth is needed when a process embeds a type, for instance as the payload of an output prefix, since the embedded type must be checked relative to the current type-binder depth.

The structural recursion evaluates each constructor by incrementing the appropriate depth counter according to the number and sort of binders introduced. Channel binders increase the channel depth $k$, while type binders increase the type depth $n$. For example, \texttt{tensor} binds a single continuation channel, incrementing the depth to $k+1$, whereas \texttt{cut} binds two dual endpoints simultaneously, incrementing the depth to $k+2$. Conversely, \texttt{input} binds a type variable, leaving $k$ unchanged while incrementing $n$ to $n+1$. The \texttt{server} constructor therefore requires local closure of \texttt{x}, \texttt{zs}, and \texttt{P}. Constructors introducing no binders, leave both counters unchanged

\begin{lstlisting}[language=Lean4]
def Proc.lc : Nat -> Nat -> Proc -> Prop
  | _, _, .nil            => True
  | k, n, .one x P        => x.lc k /-$\land$-/ P.lc k n
  | k, n, .tensor x P     => x.lc k /-$\land$-/ P.lc (k + 1) n
  | k, n, .cut P          => P.lc (k + 2) n
  | k, n, .input x P      => x.lc k /-$\land$-/ P.lc k (n + 1)
  | k, n, .duplicate x P  => x.lc k /-$\land$-/ P.lc (k + 1) n
  | ...
\end{lstlisting}

At the leaves, \texttt{Channel.lc} checks that any bound index is strictly within the current depth, while free channels are trivially locally closed. For dependency sets, \texttt{Finset.lc} requires every channel in the set to satisfy \texttt{Channel.lc k}:

\begin{lstlisting}[language=Lean4]
def Channel.lc : Nat -> Channel -> Prop
  | _, .free _   => True
  | k, .bound i  => i < k

def Finset.lc (zs : Finset Channel) (k : Nat) : Prop :=
  /-$\forall$-/ z /-$\in$-/ zs, z.lc k
\end{lstlisting}

A process is considered globally \emph{closed} when it contains no dangling indices of either sort, meaning \texttt{Proc.lc 0 0} holds. This is registered as the abbreviation \texttt{Proc.lc\_0}.

\paragraph{Free names and freshness} \path{Processes/Names.lean} defines \texttt{Proc.f~: Proc $\to$ Finset FPName} to compute the free channel names of a process. The function traverses the syntax tree structurally, collecting all explicit free channel identifiers into a finite set. Since locally nameless binders are represented using anonymous indices, bound channels contribute nothing to this set.

For constructors carrying explicit subject channels, such as \texttt{tensor} and \texttt{link}, the free names of those channels are combined with the recursively computed free names of their continuations. Constructors without explicit channel identifiers of their own, such as \texttt{cut}, contribute only the free names recursively obtained from their continuations. The \texttt{server} constructor contributes the free names of its subject channel, its dependency set and continuation:

\begin{lstlisting}[language=Lean4]
def Proc.f : Proc -> Finset FPName
  | .cut P          => P.f
  | .par P Q        => P.f /-$\cup$-/ Q.f
  | .link x y       => x.f /-$\cup$-/ y.f
  | .tensor x P     => x.f /-$\cup$-/ P.f
  | .one x P        => x.f /-$\cup$-/ P.f
  | .server x zs P  => x.f /-$\cup$-/ zs.f /-$\cup$-/ P.f
  | .nil        => {}
  | ...
\end{lstlisting}

At the leaves, \texttt{Channel.f} returns the singleton set for free channels and the empty set for bound indices. For dependency sets, \texttt{Finset.f} collects free names across all channels in the set via \texttt{biUnion}:

\begin{lstlisting}[language=Lean4]
def Channel.f : Channel -> Finset FPName
  | .free x  => {x}
  | .bound _ => {}

def Finset.f (zs : Finset Channel) : Finset FPName :=
  zs.biUnion Channel.f
\end{lstlisting}

The resulting finite set is used by \path{Processes/Fresh.lean} to generate names outside a forbidden context. Since free process names are natural numbers, a fresh name for a finite set $L$ is computed as \texttt{freshName L} $= \sup(L) + 1$, with \texttt{fresh\_is\_fresh} confirming that every element of $L$ is strictly smaller than this value. The lemmas \texttt{exists\_one\_fresh} and \texttt{exists\_two\_fresh} then guarantee one or two distinct names outside $L$, providing witnesses for the co-finite quantification premises used throughout the typing and transition rules, in particular for restriction, where two fresh and distinct endpoints must be introduced simultaneously.

\paragraph{Substitution} The process syntax supports two substitution operations, reflecting its two-sorted binding structure. Name substitution is defined in \path{Processes/SubstNames.lean} as the function \texttt{Proc.substNames (R T~: FPName)~: Proc $\to$ Proc}, replacing all explicit free occurrences of the target name $T$ with the replacement name $R$. Since bound channels are represented by De Bruijn indices, name substitution only acts on explicit free channel leaves and leaves binders untouched. Consequently, the operation is capture-avoiding by construction and does not require $\alpha$-renaming or additional freshness side conditions.

Name substitution is defined in \path{Processes/SubstNames.lean} as \texttt{Proc.substNames (R T~: FPName)~: Proc $\to$ Proc}, replacing all explicit free occurrences of $T$ with $R$. At the leaves, \texttt{Channel.subst} replaces a matching free channel and leaves bound indices unchanged; dependency sets are handled pointwise by \texttt{Finset.subst}:

\begin{lstlisting}[language=Lean4]
def Channel.subst (R T : FPName) : Channel -> Channel
  | .free x  => if x == T then .free R else .free x
  | .bound i => .bound i

def Finset.subst (zs : Finset Channel) (R T : FPName) : Finset Channel :=
  zs.image (fun u => u.subst R T)
\end{lstlisting}

Type substitution is defined in \path{Processes/SubstTypes.lean} as \texttt{Proc.substTypes (A~: Types) (k~: Nat)~: Proc $\to$ Proc}, substituting $A$ for the De Bruijn type index $k$ throughout a process. Whenever the traversal encounters an embedded type, such as the payload of an output prefix, it delegates to the type-level substitution operation \texttt{Types.subst}. When crossing an \texttt{input} prefix, which binds a type variable, the target depth is incremented and the substituted type is shifted, mirroring the binder case of \texttt{Types.subst} from \cref{subsubsec:stypes}:

\begin{lstlisting}[language=Lean4]
def Proc.substTypes (A : Types) (k : Nat) : Proc -> Proc
  | .input x P => .input x (P.substTypes (A.shift 0 1) (k + 1))
\end{lstlisting}

A consequence of this representation is that no analogous channel shifting operation is required. In a pure De Bruijn encoding, variables are represented as relative indices and must be shifted when crossing binders. Free channels, however, are represented as global identifiers rather than relative positions, so their representation is unaffected by binder depth. This avoids structural adjustment of channel names during substitution and simplifies the process-level infrastructure.

\paragraph{Type shifting}
\path{Processes/SubstTypes.lean} also defines \texttt{Proc.shiftTypes (d c~: Nat)~: Proc $\to$ Proc}, which lifts the type-level shifting operation to processes. The traversal is uniform across most constructors, delegating to \texttt{Types.shift} whenever an embedded type is encountered, such as the payload of an \texttt{output} prefix. The only non-trivial case is \texttt{input}, which binds a type variable and therefore increments the cutoff depth $d$ before traversing its continuation, mirroring the binder case of \texttt{Types.shift}:

\begin{lstlisting}[language=Lean4]
def Proc.shiftTypes (d c : Nat) : Proc -> Proc
  | .output x P A  => .output x (P.shiftTypes d c) (A.shift d c)
  | .input x P     => .input x (P.shiftTypes (d + 1) c)
  | ...
\end{lstlisting}

\paragraph{Structural Properties}
\path{Processes/Lemmas.lean} establishes the fundamental structural properties required by the later typing and operational metatheory. The lemmas fall into three groups.

The first group supports the typing invariants. The lemmas
\path{Proc.f_open_erase} and \path{Proc.f_open_two_erase} establish that
opening a process with fresh names and then erasing those names from its
free-name set recovers the original free names. They are used in the proof
of \path{Typing_f_eq_names}. The lemmas \path{Proc.lc_of_open_gen} and
\path{Proc.lc_of_open_two} show that opening a locally closed abstraction
with locally closed names yields a locally closed process. They therefore
support the proof of \path{Typing_preserves_lc}, which establishes that
well-typed processes are locally closed.

The second group supports the substitution lemmas. The lemmas
\path{Proc.open_substNames_comm} and \path{Proc.openCut_substNames_comm}
establish that opening commutes with name substitution. Their counterparts
for type substitution, \path{Proc.open_substTypes_comm} and
\path{Proc.openCut_substTypes_comm}, establish the analogous property for
substitution of types under binders. These results are used in the
typability proof, where co-finite witnesses from the typing rules must be
reconciled with the concrete names introduced by process transitions.

The third group supports freshness reasoning. \texttt{Proc.not\_mem\_f\_open} states that a name fresh for both a process and a channel does not appear in the opened process, providing the freshness conditions needed in the typability cases. These results provide the core infrastructure required for the transition semantics developed in subsequent chapters.

\paragraph{Notation} \path{Processes/Notation.lean} introduces process prefix notation mirroring the locally nameless syntax established in \cref{subsec:locally-nameless}. For example, {$\phl{\dsend{\texttt{\#x}}{\bullet}{\texttt{P}}}$} maps to \texttt{Proc.tensor (\#x) P} and {$\phl{\res{(\bullet,\bullet)}{\texttt{P}}}$} maps to \texttt{Proc.cut P}. Parallel composition and the terminated process are written {$\phl{P \pp Q}$} and {$\phl{\nil}$} respectively. The full notation is listed in \cref{lst:app-lean-process-notation}.

\subsubsection{Environments}\label{subsubsec:environments}
Environments are defined in \path{Environment/Basic.lean} as 
\texttt{Env}, an abbreviation for a list of channel-type pairs:

\begin{lstlisting}[language=Lean4]
abbrev Elem := (FPName /-$\times$-/ Types)
abbrev Env  := List Elem
\end{lstlisting}

The choice of \texttt{List} as the underlying representation deserves explanation. Theoretical environments are unordered and duplicate-free, suggesting \texttt{Finset} as a natural implementation. However, since \texttt{Finset} is implemented as a quotient over lists, it complicates structural induction, pattern matching, and inversion over environments. This proved inconvenient in a development where typing derivations are frequently inverted and typing environments must be rearranged explicitly. A second attempt using association lists (\texttt{AList}) encountered similar proof-engineering difficulties. The final design therefore uses plain lists and recovers the unordered structure through an explicit permutation relation, trading quotient reasoning for structural induction and simpler interaction with Lean's tactic machinery.

\paragraph{Recovering the PCM structure} Merging two environments is 
Environment composition is implemented as list concatenation, yielding a simple total merge operation:

\begin{lstlisting}[language=Lean4]
abbrev Env.merge (/-$\Gamma~\Delta$-/ : Env) : Env := /-$\Gamma$-/ ++ /-$\Delta$-/
infixl:69 "/-$,$-/" => Env.merge
\end{lstlisting}

Because Lean already reserves the ordinary comma for syntactic purposes, the implementation uses a visually similar comma-like symbol for environment merge. In the thesis presentation, this is rendered as the conventional comma notation for typing environments.

This representation does not make environments a partial commutative monoid by definition. List concatenation is total and order-sensitive, meaning that associativity and identity are inherited from append, while commutativity must be recovered up to permutation. The formalisation therefore uses Lean's built-in \texttt{List.Perm} relation, exposed through the common \texttt{HasPerm} interface and written $\thl{\Gamma \sim \Delta}$. The corresponding monoidal laws include:

\begin{lstlisting}[language=Lean4] 
lemma Env.merge_unitL (/-$\Gamma$-/ : Env) : /-$\envmerge{\emptyhyp}{\Gamma}$-/ = /-$\Gamma$-/ 
lemma Env.merge_unitR (/-$\Gamma$-/ : Env) : /-$\envmerge{\Gamma}{\emptyhyp}$-/ = /-$\Gamma$-/
lemma Env.merge_assoc (/-$\Gamma~\Delta~\Xi$-/ : Env) : /-$\envmerge{\envmerge{\Gamma}{\Delta}}{\Xi}$-/ = /-$\envmerge{\Gamma}{\envmerge{\Delta}{\Xi}}$-/ 
lemma Env.merge_comm (/-$\Gamma~\Delta$-/ : Env) : /-$\perm{\envmerge{\Gamma}{\Delta}}{\envmerge{\Delta}{\Gamma}}$-/
\end{lstlisting}

The partiality condition is enforced separately by predicates on the merged resources. The function \texttt{Env.names} extracts the domain of an environment as a finite set of channel names. Mutual compatibility is expressed by disjointness of these domains, while internal linearity is expressed by the absence of duplicate names:

\begin{lstlisting}[language=Lean4]
def Env.names (/-$\Gamma$-/ : Env) : Finset FPName := (/-$\Gamma$-/.map Prod.fst).toFinset 
def Env.disjoint (/-$\Gamma~\Delta$-/ : Env) : Prop := Disjoint /-$\Gamma$-/.names /-$\Delta$-/.names
def Env.Nodup (/-$\Gamma$-/ : Env) : Prop := (/-$\Gamma$-/.map Prod.fst).Nodup
\end{lstlisting}

The connection between these predicates and merge is captured by
\texttt{Env.Nodup\_merge\_iff}, which states that a merged environment is
linear exactly when both component environments are individually linear and
their domains are disjoint:

\begin{lstlisting}[language=Lean4]
lemma Env.Nodup_merge_iff {/-$\Gamma~\Delta$-/ : Env} :
  (/-$\Gamma$-/,/-$\Delta$-/).Nodup /-$\leftrightarrow$-/ (/-$\Gamma$-/.Nodup /-$\land$-/ /-$\Delta$-/.Nodup /-$\land$-/ /-$\Gamma$-/.disjoint /-$\Delta$-/) := by ...
\end{lstlisting}

The proof reduces directly to the corresponding property of list append,
\texttt{List.nodup\_append}, together with the finite-set formulation of
environment-domain disjointness.

\paragraph{Server usability} The typing rule for server replication requires all dependency channels to carry exponential request types. This side condition is captured by \texttt{Env.serverUsable}, which asserts that every type in an environment satisfies \texttt{Types.isServerUsable}, i.e.\ has the form {$\thl{\query B}$}.

\begin{lstlisting}[language=Lean4]
def Env.serverUsable (/-$\Gamma$-/ : Env) : Prop :=
  /-$\forall$-/ p, p /-$\in~\Gamma$-/ -> p.snd.isServerUsable
prefix:max "?/-$_\texttt{e}$-/" => Env.serverUsable
\end{lstlisting}

\paragraph{Lifted operations} Since environments contain types, the locally nameless operations from \cref{subsubsec:stypes} are lifted pointwise over the type component of each \texttt{Elem}. Local closure, type shifting, name substitution, and type substitution are all defined by mapping over the list. The file \path{Environment/Lemmas.lean} proves that these operations preserve the names, disjointness, nodup, and permutation properties of environments.

The interaction between shifting and local closure is captured by \texttt{Env.lc\_shift\_inv}, which states that shifting an environment by one preserves local closure: $(\Gamma^+).\texttt{lc}(n+k+1) \iff \Gamma.\texttt{lc}(n+k)$. Shifting increments all free type indices, so an environment locally closed at depth $n+k$ becomes locally closed at depth $n+k+1$ after shifting, and vice versa. The specialisation \texttt{Env.lc\_shift\_inv\_0} is used in the \texttt{forall\_} case of \texttt{Typing\_preserves\_lc} to recover local closure of the unshifted environment from that of the shifted one.

\subsubsection{Hyperenvironments}\label{subsubsec:hyperenvironments} Hyperenvironments are defined in \path{HyperEnvironment/Basic.lean} as \texttt{HyperEnv}, an abbreviation for a list of environments:

\begin{lstlisting}[language=Lean4]
abbrev HyperEnv := List Env
abbrev HyperEnv.merge (/-$\hyp{G}$-/ /-$\hyp{H}$-/ : HyperEnv) : HyperEnv := /-$\hyp{G}$-/ ++ /-$\hyp{H}$-/
infixl:55 " /-$\pp_\texttt{h}$-/ " => HyperEnv.merge
\end{lstlisting}

As for environments, merging is implemented as list concatenation, using {$\thl{\emptyhyp}$} as the unit and {$\thl{\hypermerge{\hyp{G}}{\hyp{H}}}$} as notation for composition. Associativity and unit laws therefore follow from the underlying list structure. However, recovering the commutative structure requires more than the ordinary list permutation relation, since hyperenvironments are lists whose elements are themselves environments considered modulo permutation.

\paragraph{Deep permutation} 
For environments, Lean's \texttt{List.Perm} relation is sufficient, since it allows arbitrary reordering of channel-type pairs. For hyperenvironments, however, permutation must operate at two levels: it must allow reordering of component environments, and it must also respect permutation equivalence inside each component environment.

For example, consider the hyperenvironment containing a single component environment {$\thl{[\cht{x}{A}, \cht{y}{B}]}$}. Ordinary \texttt{List.Perm} treats this component environment as an opaque element, so it does not identify it with {$\thl{[\cht{y}{B}, \cht{x}{A}]}$}. The custom relation \texttt{HyperEnv.Perm} instead permits component environments to be replaced by permutation-equivalent environments.

% \begin{example}
%   \begin{highlight}
%     Consider the hyperenvironment $\thl{[\cht{x}{A}, \cht{y}{B}]}$, consisting of a single environment with two channel-type pairs. Under \texttt{List.Perm}, this would \emph{not} be equivalent to $\thl{[\cht{y}{B}, \cht{x}{A}]}$, since the single environment element is treated as an opaque value. Under \texttt{HyperEnv.Perm}, the \texttt{cons} constructor permits the head environment to be replaced by any permutation-equivalent environment, so $\thl{[\cht{x}{A}, \cht{y}{B}] \sim [\cht{y}{B}, \cht{x}{A}]}$ holds via \texttt{cons} with the environment permutation $\thl{\cht{x}{A}, \cht{y}{B} \sim \cht{y}{B},\cht{x}{A}}$.
%   \end{highlight}
% \end{example}

\begin{lstlisting}[language=Lean4]
inductive HyperEnv.Perm : HyperEnv -> HyperEnv -> Prop where
  | nil  : Perm [] []
  | cons : {/-$\Gamma~\Delta$-/ : Env} {/-$\hyp{G~H}$-/ : HyperEnv} : /-$\perm{\Gamma}{\Delta}$-/ -> Perm /-$\hyp{G}~\hyp{H}$-/ -> Perm (/-$\Gamma :: \hyp{G}$-/) (/-$\Delta :: \hyp{H}$-/)
  | swap : {/-$\Gamma~\Delta$-/ : Env} {/-$\hyp{G}$-/ : HyperEnv} : Perm (/-$\Gamma :: \Delta :: \hyp{G}$-/) (/-$\Delta :: \Gamma :: \hyp{G}$-/)
  | trans {/-$\hyp{G~H~J}$-/ : HyperEnv} : Perm /-$\hyp{G~H}$-/ -> Perm /-$\hyp{H~J}$-/ -> Perm /-$\hyp{G~J}$-/
\end{lstlisting}

The key constructor is \texttt{cons}. Unlike ordinary list permutation, it does not require the head environments to be syntactically identical, it only requires them to be permutation-equivalent. Thus \texttt{HyperEnv.Perm} is a deep permutation relation, propagating equivalence both across the ordering of component environments and within the environments themselves.

\paragraph{Well-formedness} Hyperenvironment well-formedness is decomposed into two predicates. The predicate \texttt{HyperEnv.Nodup} requires each component environment to be internally linear, while \texttt{HyperEnv.PairwiseDisjoint} requires distinct component environments to have disjoint domains:

\begin{lstlisting}[language=Lean4]
def HyperEnv.Nodup (/-$\hyp{G}$-/ : HyperEnv) : Prop :=
  /-$\forall~\Gamma, ~\Gamma \in \hyp{G}$-/ -> Env.Nodup /-$\Gamma$-/

def HyperEnv.PairwiseDisjoint (/-$\hyp{G}$-/ : HyperEnv) : Prop :=
  List.Pairwise Env.disjoint /-$\hyp{G}$-/
\end{lstlisting}

The distinction is important because the two predicates rule out different violations of linearity. For example, assuming $x$, $y$, and $z$ are distinct names:

\begin{highlight}  
  \begin{itemize}
    \item $\thl{\hypermerge{[\cht{x}{A}]}{[\cht{y}{B}, \cht{z}{C}]}}$ satisfies both predicates.
    \item $\thl{\hypermerge{[\cht{x}{A}, \cht{x}{B}]}{[\cht{y}{C}]}}$ violates \texttt{Nodup}, since $x$ appears twice within one component environment.
    \item $\thl{\hypermerge{[\cht{x}{A}]}{[\cht{x}{B}, \cht{y}{C}]}}$ violates \texttt{PairwiseDisjoint}, since $x$ appears in two distinct components.
  \end{itemize}
\end{highlight}
  
Together, these predicates enforce global linearity: every channel appears at most once across the whole hyperenvironment.

\paragraph{Lifted operations}
The operations on environments are lifted once more to hyperenvironments by applying them pointwise to each component environment. Thus, type shifting, name substitution, and type substitution on hyperenvironments follow the same pattern as the corresponding operations on environments. The file \path{HyperEnvironment/Lemmas/Basic.lean} proves that these lifted operations preserve the structural invariants used later in the development, including names, disjointness, pairwise disjointness, and deep permutation. For example, preservation of deep permutation under shifting is proved by induction on the proof of the hyperenvironment permutation relation, using the corresponding environment-level permutation lemmas. Since these definitions are obtained uniformly from the environment-level construction, they are not reproduced in full here. The complete definitions and proofs are included in the accompanying Lean archive.

\subsubsection{Typing Judgements}\label{subsubsec:judgements}
The typing relation is defined in \path{Judgement/Basic.lean} as the inductive predicate \texttt{Typing}:

\begin{lstlisting}[language=Lean4]
inductive Typing : Nat -> Proc -> HyperEnv -> Prop
\end{lstlisting}

We write {$\judge{n}{P}{\hyp{G}}$} for a derivation of this predicate. The index $n$ tracks the current type-binder depth, while the remaining indices record the process being typed and its associated typing environment. This intrinsic indexing is later used by the erasure maps in the semantics and metatheory. The full inductive definition, including the typing constructors and the exchange rules, is given in \cref{app:judgement-basic-definition}.

\paragraph{Type-depth indexing}
The type-depth index is relevant whenever the derivation crosses a polymorphic binder. For example, the \texttt{forall\_} constructor increments the depth from $n$ to $n+1$ and shifts the surrounding environment to keep embedded type indices in scope:

\begin{lstlisting}[language=Lean4]
| forall_ :
    Typing (n + 1) P [/-$\cht{\texttt{x}}{\texttt{B}} :: \Gamma^{+}$-/] ->
    Typing n (#x/-$\dparenL\diamond\dparenR$-/.P) [/-$\cht{\texttt{x}}{\forall.\texttt{B}} :: \Gamma$-/]
\end{lstlisting}

The shift {$\thl{\typeshiftsingle{\Gamma}}$} abbreviates shifting the type indices in $\Gamma$ by one starting at depth $0$, mirroring the binder-sensitive shifting used by type substitution in \cref{subsubsec:stypes}.

The depth index is also relevant for the~\ref{rule:pill-mix} rule, which requires both sub-derivations to share the same depth $n$. When derivations are available at different depths, they can be brought into alignment using \texttt{Typing\_weakening}. This lemma states that a derivation at depth $n$ can be lifted to depth $n+c$ by shifting the embedded type indices in both the process and the hyperenvironment:

\begin{lstlisting}[language=Lean4]
lemma Typing_weakening :
  Typing n P /-$\hyp{G}$-/ -> /-$\forall$-/ d c, Typing (n + c) (P /-$\uparrow$-/ d, c) (/-$\hyp{G}$-/ /-$\uparrow$-/ d, c) := by ...
\end{lstlisting}

This provides the weakening principle needed to compose derivations across polymorphic binders while keeping embedded type indices in scope.

\paragraph{Exchange and explicit side conditions}
In some constructors, the formalised rule chooses an ordering different from the paper presentation so that the entry manipulated by the rule occurs at the head of the list representing its environment component. This is an implementation-oriented choice and does not affect the typing discipline. The order-insensitive interpretation of environments and hyperenvironments is recovered by exchange rules in the typing relation, which permit reasoning up to permutation:

\begin{lstlisting}[language=Lean4]
| exchange_env   : Typing n P (/-$\Gamma :: \hyp{G}$-/) -> /-$\perm{\Gamma}{\Delta}$-/ -> Typing n P (/-$\Delta :: \hyp{G}$-/)
| exchange_hyper : Typing n P /-$\hyp{G}$-/ -> /-$\perm{\hyp{G}}{\hyp{H}}$-/ -> Typing n P /-$\hyp{H}$-/
\end{lstlisting}

The exchange rules recover the unordered character of the paper presentation without quotienting environments or hyperenvironments. The complementary issue is partiality: although merging is implemented as total list concatenation, typing rules carry explicit disjointness and freshness premises to ensure that only valid linear compositions are formed. For example, \texttt{mix} requires the two hyperenvironments to be disjoint, while prefix rules such as \texttt{tensor} and \texttt{parr} require freshness premises ensuring that subject channels do not already appear in the continuation environment.

The same design principle reappears later in the operational semantics, where transitions must also respect permutation equivalence of environments and hyperenvironments.

% \paragraph{Explicit Disjointness Constraints}
% In the paper presentation of \pill{}, the disjointness of environments during operations like parallel composition or tensor is implicitly guaranteed by the structural properties of the merge operator for environments and hyperenvironments. However, because the Lean formalisation relies on total list concatenation, these disjointness requirements must be enforced explicitly at the rule level. Many typing constructors carry explicit disjointness and freshness premises to ensure that merging operations remain valid. For example, the \texttt{mix} rule requires a proof that the two hyperenvironments are mutually disjoint (\texttt{hD~: $\hyp{G}$.disjoint $\hyp{H}$}), and the \texttt{tensor} rule requires explicit proof that the subject channel $x$ does not already exist in the continuations (\texttt{hF~: x $\notin \Gamma$.names $\land$ x $\notin \Delta$.names}). While these local constraints clutter the inductive definitions compared to their paper counterparts, they are necessary to ensure that the formalised typing relation preserves the partiality of the theoretical merge operator and its underlying monoid structure. The global metatheoretical consequences of these local constraints, namely, that well-typed processes inherently preserve context linearity, are detailed in \cref{sec:metatheory}.

\paragraph{Co-finite quantification}
Binding rules use co-finite quantification as described in \cref{subsec:co-finite-quantification}. For example, the \texttt{parr} constructor types an input prefix by requiring the opened continuation to be well typed for every fresh payload name outside a finite set $L$:

% \begin{lstlisting}[language=Lean4]
% | cut (L : Finset FPName) :
%     /-$\forall$-/x /-$\notin$-/ L, /-$\forall$-/y /-$\notin$-/ L, x /-$\neq$-/ y -> Typing n (/-$\dopen{P}{\texttt{\#x}, \texttt{\#y}}$-/) (/-$\hypermerge{G}{\hypermerge{[\cht{\texttt{x}}{\texttt{A}} :: \Gamma]}{[\cht{\texttt{y}}{\texttt{A}}^\bot :: \Delta]}}$-/) ->
%     Typing n (/-$\dres{\texttt{P}}$-/) (/-$\hypermerge{\hyp{G}}{[\Gamma, \Delta]}$-/)
% \end{lstlisting}

% The premise holds for any two distinct names $x, y$ outside the finite set $L$. This design serves two complementary purposes. When \emph{constructing} a typing derivation, the prover chooses $L$ to be large enough that any witness outside it is guaranteed fresh, typically the union of all free names currently in scope, and then uses \texttt{exists\_two\_fresh} to produce concrete witnesses. When \emph{using} a typing derivation, for example during inversion or induction, the universal quantifier allows the prover to instantiate $x$ and $y$ as whatever fresh names the current proof goal requires, rather than being tied to the specific names chosen during construction.

\begin{lstlisting}[language=Lean4]
| parr (hF : x /-$\notin \Gamma$-/.names) (L : Finset FPName) :
    (/-$\forall$-/ y /-$\notin$-/ L, Typing n (/-$\dopen{\texttt{P}}{\texttt{\#y}}$-/) [/-$\cht{\texttt{y}}{\texttt{A}} :: \cht{\texttt{x}}{\texttt{B}} :: \Gamma$-/]) ->
    Typing n (/-$\drecv{\texttt{x}}{\bullet}{\texttt{P}}$-/) [/-$\cht{\texttt{x}}{\texttt{A} \parr \texttt{B}} :: \Gamma$-/]
\end{lstlisting}

Here, the process carries no explicit payload name; the bound occurrence in the continuation is instantiated by opening $P$ with the fresh name $y$. The premise \texttt{hF} enforces that the subject channel $x$ is not already present in the continuation environment. Rules binding multiple names, such as \texttt{cut}, follow the same pattern but quantify over two distinct fresh names.

\paragraph{Structural invariants} \path{Judgement/Names.lean} establishes the central name invariant for the typing relation, named \texttt{Typing\_f\_eq\_names}. It states that, for any well-typed process, the free names of the process coincide exactly with the domain of its hyperenvironment.

\begin{highlight}
\[
\judge{n}{P}{\hyp{G}} \implies \phl{P}.f = \thl{\hyp{G}}.names
\]
\end{highlight}

The proof proceeds by induction on the typing derivation. Most cases follow by unfolding \texttt{Proc.f} and \texttt{HyperEnv.names} and rewriting with the induction hypothesis. In the co-finite binding cases, the proof instantiates fresh names, applies the induction hypothesis to the opened process, and then uses \texttt{Proc.f\_open\_erase} to cancel the introduced names from the free name set and recover equality for the closed process.

This ensures exact correspondence between process free names and typed environment entries: no free process channel is left untyped, and no environment entry is unused.

Building on this,~\path{Judgement/Properties/Linearity.lean} proves that 
any well-typed hyperenvironment is pairwise disjoint and all component 
environments have no duplicate names.

\begin{highlight}
\[
\judge{n}{P}{\hyp{G}} \implies 
\texttt{Nodup}~\thl{\hyp{G}} \land \thl{\hyp{G}}.\texttt{PairwiseDisjoint}
\]
\end{highlight}

The proof proceeds by induction on the typing derivation. Most non-binding rules are discharged uniformly by unfolding the relevant definitions and applying the induction hypothesis. The co-finite binding cases (\texttt{cut}, \texttt{tensor}, \texttt{parr}, and contraction \texttt{c}) require instantiating fresh names and reconstructing both nodupness and disjointness of the component environments from the opened induction hypothesis. The exchange cases use preservation of these properties under permutation. 

Together, \texttt{Typing\_f\_eq\_names} and \texttt{Typing\_preserves\_linearity} guarantee that typing derivations can only be constructed for well-formed, linear contexts. In particular, a well-typed process cannot contain duplicate free channel occurrences: by the name correspondence, duplicate free names would require duplicate entries in the hyperenvironment, contradicting pairwise disjointness. 

A third invariant, \texttt{Typing\_preserves\_lc}, establishes that every well-typed process is locally closed and that every component environment in its hyperenvironment is locally closed at the current type-binder depth. The proof is split into \texttt{Typing\_preserves\_lc\_proc} for the process and \texttt{Typing\_preserves\_lc\_context} for the hyperenvironment, then packaged together. Both proceed by induction on the typing derivation. The co-finite binding cases use \texttt{Proc.lc\_of\_open\_gen} and \texttt{Proc.lc\_of\_open\_two} to recover local closure of the closed process from that of the opened one. The \texttt{forall\_} and \texttt{exists\_} cases additionally require \texttt{Env.lc\_shift\_inv\_0} and \path{Types.lc_subst_inv_0} to invert the effect of shifting and substitution on the environment and type indices respectively.

\paragraph{Substitution}
\path{Judgement/Subst.lean} establishes that typing is stable under both forms of substitution. \texttt{Typing\_substNames} states that if $\judge{n}{P}{\hyp{G}}$ and $y$ does not appear in $\thl{\hyp{G}}$ except possibly as $x$, then substituting $y$ for $x$ throughout yields a well-typed process under the correspondingly substituted hyperenvironment. \texttt{Typing\_substTypes} gives the analogous result for type substitution, where substituting a type $A$ for De Bruijn index $k$ throughout a derivation yields a well-typed process at depth $n-1$. Both proofs proceed by induction on the typing derivation and rely on the commutation lemmas from \cref{subsubsec:processes}.

\subsection{Semantics}\label{subsec:semantics}
The dynamic behaviour of the \pimll{} fragment is formalised in the \path{Semantics/} namespace. Following the erasure structure described in \cref{subsec:operational-semantics}, the development contains three related transition systems: a typed transition system over typing derivations, and two projected systems describing the induced process and environment behaviour.

\begin{itemize}
    \item \textbf{\texttt{TypingStep}$_\texttt{m}$}: the primary, resource-aware LTS over typing derivations (\path{JudgementStep/Basic.lean});
    \item \textbf{\texttt{ProcStep}$_\texttt{m}$}: the process-level LTS obtained by forgetting typing resources (\path{ProcStep/Basic.lean});
    \item \textbf{\texttt{EnvStep}$_\texttt{m}$}: the resource-level LTS describing the corresponding evolution of hyperenvironments (\path{EnvStep/Basic.lean}).
\end{itemize}

The complete inductive definitions of these three transition systems are given in \cref{lst:app-typingstep,lst:app-procstep,lst:app-envstep}.

\paragraph{Labels}\label{subsubsec:labels}
Transition labels are formalised in \path{Labels.lean}, directly realising the label algebra introduced in \cref{subsec:operational-semantics}. Although the operational semantics mechanised here target \pimll{}, the action vocabulary is defined for the full \pill{} calculus to support future extensions. The free and introduced name functions $\fs$ and $\is$ are realised as \texttt{Lbl.f} and \texttt{Lbl.i}, computed by structural recursion on the label. The disjointness condition on \texttt{par} labels is enforced as the decidable predicate \texttt{Lbl.WF}, which appears as an explicit side condition in the parallel synchronisation rules.

The core action type, \texttt{Act}, captures observable communication events, including empty communication, channel transmission, type instantiation, and server interaction. Selection and server actions are parameterised by the auxiliary datatype \texttt{Mu}. The \texttt{Lbl} inductive then extends observable actions with the silent transition $\tau$, explicit session-link labels, and a parallel constructor combining two observable actions directly, reflecting the synchronized action labels used by the parallel rules.

\begin{lstlisting}[language=Lean4]
inductive Act : Type
  | one       (x : FPName)
  | tensor    (x y : FPName)
  | output    (x : FPName) (A : Types)
  | muBrack   (x : FPName) (/-$\mu$-/ : Mu)
  | ...

inductive Lbl : Type
  | tau
  | link  (x y : FPName)
  | act   (p : Act)
  | par   (l l' : Act)
\end{lstlisting}

Each label defines computable sets of free names (\texttt{Lbl.f}) and introduced names (\texttt{Lbl.i}), which are used in the side conditions for the \cref{rule:pill-mix-1,rule:pill-proc-mix-2,rule:pill-mix-sync}. The label notation is overloaded through the \texttt{HasBracket} and \texttt{HasParen} typeclasses. Since labels record concrete observable actions, their subjects are free process names rather than locally nameless channels. The overloading is therefore internal to the label language. Bracketed and parenthesised labels are distinguished by the type of their payload, allowing empty communication, channel transmission, type communication, and server actions to share a compact notation. The corresponding notation instances are given in \cref{lst:app-lean-label-notation}.

\subsubsection{The Typed Transition System}\label{subsubsec:judgementstep}
The primary LTS, \texttt{TypingStep}$_\texttt{m}$, is a relation between typing derivations. Its constructors mirror the operational rules shown in \cref{fig:mpill-sos}, but make the type-theoretic content of each step explicit: every transition carries a typing derivation as its source and produces a typing derivation as its target. The system is therefore intrinsically typed.

\begin{lstlisting}[language=Lean4]
inductive TypingStep/-$_\texttt{m}$-/ : 
  Typing n P /-$\hyp{G}$-/ /-$\to$-/ Lbl /-$\to$-/ Typing n' P' /-$\hyp{G}$-/' /-$\to$-/ Prop
\end{lstlisting}

As established previously, both environment and hyperenvironment composition are formalised using total list appends. Consequently, the explicit disjointness proofs required by the static \texttt{Typing} relation to safely mix environments must propagate directly into the dynamic \texttt{TypingStep}$_\texttt{m}$ relation. For instance, the \texttt{par$_1$} constructor requires explicit hypotheses (\texttt{hD1} and \texttt{hD2}) to guarantee that the hyperenvironments remain strictly disjoint both before and after the transition:

\begin{lstlisting}[
  language=Lean4,
  caption={The \texttt{par}$_1$ constructor of the typed transition relation, with explicit pre- and post-transition disjointness premises.}, label={lst:typingstep-par1}
  ]
| par/-$_1$-/
    (hD1 : /-$\hyp{G}$-/.disjoint /-$\hyp{H}$-/) (hD2 : /-$\hyp{G}$-/'.disjoint /-$\hyp{H}$-/) (disj : l.i /-$\cap$-/ Q.f = /-$\emptyset$-/)
    (h : TypingStep/-$_\texttt{m}$-/ /-$\der{D}$-/ l /-$\der{D}$-/') :
    TypingStep/-$_\texttt{m}$-/
      (Typing.mix hD1 /-$\der{D}$-/ /-$\der{E}$-/) l (Typing.mix hD2 /-$\der{D}$-/' /-$\der{E}$-/)
\end{lstlisting}

The post-state disjointness proof \texttt{hD2} is included explicitly as a proof-engineering convenience. Strictly stepping typing derivations can expose structural artifacts that are usually hidden in the paper presentation. For example, in \cref{fig:cut-unit-trans}, the intermediate derivation is typed by $\thl{\emptyhyp \pp \cht{y}{1}}$ rather than simply $\thl{\cht{y}{1}}$, because the~\ref{rule:pill-mix} rule preserves the empty component contributed by the terminated left process. The result is valid, but reducing it to the canonical form requires applying the monoidal identity laws of the hyperenvironment explicitly, rather than by definitional equality. The final $\equiv$ step in the figure, which additionally uses process congruence to identify $\phl{\nil \pp \nil}$ with $\phl{\nil}$, is not currently automated because structural congruence has not been mechanised. A subtler asymmetry concerns the co-finite quantification style used in the \texttt{Typing} and \texttt{Typing\allowbreak{}Step}$_\texttt{m}$ relations. In \texttt{Typing}, binding rules use the binder-style notation $\forall\, y \notin L$ as part of the constructor premise. In \texttt{TypingStep}$_\texttt{m}$, the corresponding constructors instead carry the co-finite premise as an implicit field \texttt{huniq} and record the concrete instantiation point as a separate explicit premise \texttt{hy}. This makes the specific fresh name chosen by the transition visible at the constructor level, which simplifies pattern matching in the typability proof at the cost of a slightly more verbose inductive definition.

\subsubsection{Projected Transition Systems}\label{subsubsec:inducedlts}
The process and environment transition systems are defined to capture the two erasure views of a typed transition. \texttt{ProcStep}$_\texttt{m}$ records the process behaviour obtained by forgetting typing resources, while \texttt{EnvStep}$_\texttt{m}$ records the corresponding resource evolution. These relations are later connected to \texttt{TypingStep}$_\texttt{m}$ by the simulation theorems in \cref{subsec:session-fidelity}.

\paragraph{Process steps}
\texttt{ProcStep}$_\texttt{m}$ models the syntactic evolution of processes independently of typing resources. Unlike the typing relation, it is not indexed by a typing derivation and therefore does not use co-finite premises. Binder-opening rules instead choose concrete fresh names directly and record the required freshness as explicit side conditions. For example, the \texttt{tensor} rule opens the continuation with a concrete name $y$, requiring $y$ to be fresh for both the subject channel and the continuation:

\begin{lstlisting}[language=Lean4]
  | tensor (hF : y /-$\notin$-/ {x} /-$\cup$-/ P.f) :
      ProcStep/-$_\texttt{m}$-/ (/-$\dsend{\texttt{\#x}}{\bullet}{\texttt{P}}$-/) (/-$\dlsend{\texttt{x}}{\texttt{y}}$-/) /-$\dopen{\texttt{P}}{\texttt{\#y}}$-/
\end{lstlisting}

This creates a mismatch with the co-finite formulation of the typing rules:
\texttt{ProcStep}$_\texttt{m}$ records the concrete name chosen by an
operational step, while the typing rule provides a premise for all names
outside a finite exclusion set. The reconciliation of these two views is
handled by the typability proof in \cref{subsec:session-fidelity}.

\paragraph{Environment steps}
The structural evolution of hyperenvironments, written $\hyp{G} \xrightarrow{l} \hyp{H}$, is formalised by \texttt{EnvStep}$_\texttt{m}$. Unlike the typed transition system, \texttt{EnvStep}$_\texttt{m}$ deliberately contains only the resource transformation described by the label. For example, an input action on an endpoint typed by $\bot$ consumes that resource: $\Gamma, \cht{x}{\bot} \xrightarrow{x()} \Gamma$. Similarly, an empty output on an endpoint typed by $1$ evolves $\cht{x}{1}$ to the empty environment. These rules describe how session types evolve as actions are performed, independently of any particular process term.

The relation does not independently enforce all disjointness and well-formedness conditions. Those properties are supplied by the typing derivation in \texttt{TypingStep}$_\texttt{m}$. This separation keeps the projected resource semantics lightweight: the environment relation describes how resources change, while the typed semantics proves that these changes occur from well-formed typing environments.

The following metatheory shows that these transition systems agree: typed transitions project to process and environment transitions, and process transitions from well-typed states can be lifted back to typed transitions.
