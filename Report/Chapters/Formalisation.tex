\section{Formalisation}\label{sec:formalisation}
This section describes the mechanisation of \pill{} in Lean 4, bridging the theoretical foundations developed in~\cref{sec:background,sec:binding-architecture} and their concrete implementation. The formalisation is organised into three top-level namespaces: \texttt{PiLL.Model}, which defines the static structure of the calculus, \texttt{PiLL.Semantics}, which defines its operational behaviour, and \texttt{PiLL.SessionFidelity}, which establishes the metatheoretic results connecting the two. Each component is presented in dependency order, highlighting design decisions and divergences from~\citet{abs-2106-11818}.

\subsection{Model}\label{subsec:model}
The \texttt{Model} namespace formalizes the static structure of the full \pill{} calculus and is organized around the layered architecture introduced in~\cref{sec:background}. The mechanisation proceeds bottom-up: session types, defined in \texttt{STypes/}, provide the binding structure used by processes in \texttt{Processes/}, processes are then typed relative to environments and hyperenvironments from \texttt{Environments/} and \texttt{HyperEnvironment/}, finally, typing derivations and their metatheoretic infrastructure are collected in \texttt{Judgement/}. This includes inversion lemmas, linearity properties, substitution principles, and the co-finite freshness machinery described in~\cref{subsec:co-finite-quantification}. Shared syntactic infrastructure used across these layers is provided by \texttt{Base.lean}.

\subsubsection{Session Types}\label{subsubsec:stypes}
Session types are defined in \texttt{STypes/Basic.lean} as the inductive datatype \texttt{Types}. Following the locally nameless syntax established in \cref{subsec:locally-nameless}, type variables are isolated into a separate inductive type, \texttt{TVar}, which explicitly distinguishes between free and bound occurrences:

\begin{lstlisting}[language=Lean4]
inductive TVar : Type
  | free  (x : FTVar)   
  | bound (x : BTVar)   
\end{lstlisting}

Here, \texttt{FTVar} represents a free type variable identified by a natural number, while \texttt{BTVar} represents a bound type variable encoded as a De Bruijn index.

The remaining constructors directly mirror the theoretical grammar of the calculus. In addition, the formalisation introduces uninterpreted atomic types (\texttt{atom} and \texttt{atomDual}), representing protocol leaves not further decomposed by the session type grammar and providing the base cases for the inductive structure of the syntax. \Cref{tab:types-comparison} illustrates a representative correspondence between the paper syntax, the locally nameless representation, and the Lean implementation.

\begin{highlight}
\begin{table}[htbp]  
    \centering
    \caption{Comparison of standard, locally nameless, and Lean representations for \pill{} types.}
    \label{tab:types-comparison}
    \begin{tabular}{llll}
        \toprule
        \textbf{Standard} & \textbf{Locally Nameless} & \textbf{Lean Constructor} & \textbf{Binds} \\
        \midrule

Notably, the polymorphic binders \hl{$\thl{\forall.A}$} and \hl{$\thl{\exists.A}$} reflect the depth-indexed approach detailed in \cref{subsec:co-finite-quantification}. The constructors keep the bound De Bruijn index implicit, taking only the continuation body \texttt{A} as an argument (an underscore ``\texttt{\_}'' has been appended to the constructor names to prevent namespace collisions with Lean's built-in \texttt{forall} and \texttt{exists} keywords).

\paragraph{Duality} \texttt{Types.dual} implements duality as a structurally recursive function, mapping each constructor to its dual. For example:

\begin{lstlisting}[language=Lean4]
def Types.dual : Types -> Types
  | .tensor A B  => .parr    (dual A) (dual B)
  | .forall_ A   => .exists_ (dual A)
  | .one         => .bot
  | ...
\end{lstlisting}

The fundamental property that duality is an involution,
\hl{$\thl{{(A^\bot)}^\bot = A}$},
is proved in \path{STypes/Lemmas.lean} by structural induction.

The formalisation additionally establishes that duality preserves local closure and commutes with both shifting and substitution:
\begin{highlight}  
\begin{gather*}
\thl{A}.\texttt{lc} \iff \thl{A^\bot}.\texttt{lc} \qquad
\thl{\shiftdc{d}{c}(A^\bot) = {(\shiftdc{d}{c}A)}^\bot} \qquad
\thl{B^\bot\{A/k\}} = \thl{{(B\{A/k\})}^\bot}
\end{gather*}
\end{highlight}

\paragraph{Local closure} \texttt{STypes\slash{}Properties.lean} defines local closure for types as a depth-indexed predicate \texttt{Types.lc (k~: Nat)~: Types $\to$ Prop}, where the depth parameter $k$ tracks how many binders the recursion has traversed. 

At the leaves of the syntax tree, local closure is evaluated by the helper predicate \texttt{TVar.lc}. Because free variables are explicit they do not contain any indices, as such they are inherently locally closed at any depth. By contrast, a bound variable is only locally closed if its De Bruijn index $i$ is strictly less than the current depth $k$, ensuring it points to an enclosing scope:

\begin{lstlisting}[language=Lean4]
def TVar.lc : Nat -> TVar -> Prop
  | _, .free _   => True
  | k, .bound i  => i < k
\end{lstlisting}

The primary \texttt{Types.lc} predicate is then defined by structural recursion. For non-binding constructors, the depth parameter distributes across the sub-terms. When a variable is encountered, the predicate delegates the check to \texttt{TVar.lc}. When descending into the body of a polymorphic binder, the depth counter increments by one, bringing the newly introduced index safely into scope:

\begin{lstlisting}[language=Lean4]
def Types.lc : Nat -> Types -> Prop
  | _, .one         => True
  | k, .var v       => TVar.lc k v
  | k, .tensor A B  => A.lc k /-$\land$-/ B.lc k
  | k, .forall_ A   => A.lc (k + 1)
  | k, .exists_ A   => A.lc (k + 1)
  | ...
\end{lstlisting}

Finally, a type is defined as \emph{closed} if it contains no dangling indices at the top level, meaning it is locally closed at depth $0$. This is registered as the abbreviation \texttt{Types.lc\_0}.

\paragraph{Shifting} \path{STypes/Shift.lean} defines shifting following the standard De Bruijn shifting operation introduced in \cref{subsec:co-finite-quantification}. The operation traverses the syntax tree structurally using a cutoff depth $d$ and a shift amount $c$.

For standard connectives, shifting distributes recursively across subterms, while base constructors such as \texttt{one} and \texttt{bot} remain unchanged. When traversing a polymorphic binder like \texttt{forall\_}, the cutoff depth increments by one to account for the newly entered scope:

\begin{lstlisting}[language=Lean4]
def Types.shift (d c : Nat) : Types -> Types
  | .var v       => .var (v.shift d c)
  | .tensor A B  => .tensor (A.shift d c) (B.shift d c)
  | .forall_ A   => .forall_ (A.shift (d + 1) c)
  | t            => t
\end{lstlisting}

At the variable level, free variables remain unchanged. For bound indices, the function compares the De Bruijn index $i$ against the cutoff depth $d$. Indices satisfying $i < d$ are locally bound within the traversed scope and therefore remain unchanged. Otherwise, the index is incremented by $c$ to preserve its reference to the surrounding environment:

\begin{lstlisting}[language=Lean4]
def TVar.shift (d c : Nat) : TVar -> TVar
  | .bound i => if i < d then .bound i else .bound (i + c)
  | .free n  => .free n
\end{lstlisting}

\paragraph{Substitution} \path{STypes/Subst.lean} defines substitution as the replacement of a target De Bruijn index $k$ in a host type $B$ by a payload type $A$, denoted $B\{A // k\}$.At the variable level, the function compares a bound De Bruijn index $i$ with the target depth $k$. If $i = k$, the target index has been reached and the variable is replaced by $A$. If $i < k$, the variable is bound by an inner scope and is left unchanged. Finally, if $i > k$, the index refers to an outer binder beyond the substituted variable. Since substitution removes the binder corresponding to $k$, such indices are decremented by one to preserve their relative distance to the surrounding environment.

\begin{lstlisting}[language=Lean4]
def Types.subst (B A : Types) (k : Nat) : Types :=
  match B with
  | .var (.bound i) =>
      if i == k then A
      else if i > k then .var (.bound (i - 1))
      else .var (.bound i)
\end{lstlisting}

The operation is lifted to the full \texttt{Types} syntax by structural recursion. For ordinary connectives, substitution distributes across subterms. When descending into a polymorphic binder such as \texttt{forall\_}, the target depth is incremented to $k+1$, and the payload type $A$ is shifted by one. This prevents the free indices in $A$ from being captured by the newly entered binder:

\begin{lstlisting}[language=Lean4]
  | .forall_ B => .forall_ (B.subst (shift 0 1 A) (k + 1))
\end{lstlisting}

\paragraph{Notation} \path{STypes/Notation.lean} introduces notation mirroring the mathematical presentation from \cref{subsec:types}. The only divergence is that exponentials are written \hl{$\thl{\bang\bang A}$} and \hl{$\thl{\query\query A}$} to avoid clashes with Lean syntax.

\subsubsection{Processes}\label{subsubsec:processes}
Processes are defined in \path{Processes/Basic.lean} as the inductive type \texttt{Proc}. Following the established locally nameless architecture, channel references are partitioned into a dedicated \texttt{Channel} inductive. Explicit free channels are instantiated as concrete natural numbers (\texttt{FPName}). While the raw process syntax permits arbitrary reuse of these numbers, using \texttt{Nat} allows the formalisation to systematically compute strictly fresh names by incrementing the supremum of any finite set of existing names (mechanised in \path{Processes/Fresh.lean}). Conversely, bound channels are represented using De Bruijn indices, encoding their relative distance to the corresponding binder.

\begin{lstlisting}[language=Lean4]
inductive Channel : Type where
  | free  (x : FPName)
  | bound (x : BPName)
\end{lstlisting}

As discussed in \cref{subsec:locally-nameless}, binding constructs in the process syntax no longer carry explicit payload variables. Instead, bound occurrences are captured purely by their relative position. Comparing the standard paper grammar with the intermediate locally nameless notation and the final constructors of the \texttt{inductive Proc} type illustrates this abstraction:

\begin{highlight}  
\begin{center}
\begin{tabular}{llll}
    \toprule
    \textbf{Standard} & \textbf{Locally Nameless} & \textbf{Lean Constructor} & \textbf{Binds} \\
    \midrule
    $\phl{\send{x}{y}{P}}$ & $\phl{\send{x}{\bullet}{P}}$ & \texttt{| tensor (x~: Channel) (P~: Proc)} & 1 channel \\
    $\phl{\recv{x}{y}{P}}$ & $\phl{\recv{x}{\bullet}{P}}$ & \texttt{| parr (x~: Channel) (P~: Proc)} & 1 channel \\
    $\phl{\res{xy}{P}}$ & $\phl{\res{(\bullet, \bullet)}{P}}$ & \texttt{| cut (P~: Proc)} & 2 channels \\
    $\phl{\recvtype{x}{X}{P}}$& $\phl{x(\diamond).P}$ & \texttt{| input (x~: Channel) (P~: Proc)} & 1 type \\
    $\phl{\clientdup{x}{x'}{P}}$ & $\phl{\clientdup{x}{\bullet}{P}}$ & \texttt{| duplicate (x~: Channel) (P~: Proc)} & 1 channel \\
    \bottomrule
\end{tabular}
\end{center}
\end{highlight} 

Notice that \texttt{cut} takes only a continuation \hl{$\phl{P}$} with no explicit channel arguments, as both dual endpoints are simultaneously bound as indices $0$ and $1$ within the scope of \hl{$\phl{P}$}. Similarly, for constructs like \texttt{tensor}, \texttt{parr}, and \texttt{input}, the subject channel $x$ over which the interaction occurs is kept explicit, while the transmitted payload is anonymized into the continuation.

\paragraph{Opening and closing} \path{Processes/OpenClose.lean} defines opening and closing operations following the locally nameless principles established in \cref{subsec:opening-and-closing}. In the theoretical presentation, opening a process at depth $k$ with $x$ is denoted as \hl{$\phl{\{k \mapsto x\}P}$}, and conversely, abstracting a specific name back into a bound index is denoted as \hl{$\phl{\{k \mapsfrom x\}P}$}. 

To mechanise this in Lean, we denote explicit free channels as $\#x$ (mapping to \texttt{Channel.free x}) and introduce custom notation for these substitution operations. Expressions such as $\dopen{P}{k | \#x}$ and $\dopen{P}{k | \#x,\#y}$ denote the opening of a process by instantiating the $k$-th (and $k+1$-th) bound indices with free channels. Conversely, $\dclose{P}{k | \#x}$ and $\dclose{P}{k | \#x, \#y}$ denote the closing of a process by abstracting $x$ and $y$ back into De Bruijn indices. For convenience, the depth parameter can be omitted when operating at the innermost binder ($k=0$), simplifying the notation to $\dopen{P}{\#x,\#y}$ and $\dclose{P}{\#x,\#y}$.

Because binders are represented positionally, the depth parameter $k$ increments according to the number of channels bound by each constructor. For standard communication prefixes like \texttt{tensor}, \texttt{parr}, and the server \texttt{duplicate} operation, exactly one channel is bound, incrementing $k$ by one. The restriction constructor (\texttt{cut}) simultaneously binds two dual endpoints, requiring $k$ to increment by two. Notably, the \texttt{input} constructor binds a type variable rather than a channel. Consequently, it does not affect the channel depth parameter $k$.

\begin{lstlisting}[language=Lean4]
def Proc.open (P : Proc) (u : Channel) (k : Nat) : Proc :=
  match P with
  | .tensor x P     => .tensor (x.open u k) (P.open u (k + 1))  
  | .parr   x P     => .parr   (x.open u k) (P.open u (k + 1))  
  | .cut      P     => .cut                 (P.open u (k + 2))
  | .input  x P     => .input  (x.open u k) (P.open u k)
  | ...
\end{lstlisting}

At the leaves of the syntax tree, this recursive traversal delegates to the base case defined by \texttt{Channel.open}. For bound channels, the function evaluates the De Bruijn index $i$ against the target depth $k$, replacing it with the instantiated channel $v$ upon an exact match. Explicit free channels remain entirely unaffected:

\begin{lstlisting}[language=Lean4]
def Channel.open (u v : Channel) (k : Nat) : Channel :=
  match u with
  | bound i => if i == k then v else bound i
  | c => c
\end{lstlisting}

For restriction the \texttt{HasOpenTwo} typeclass from \path{Base.lean} is instantiated by opening sequentially: first replacing index $k+1$ with the second endpoint $v$, then replacing index $k$ with the first endpoint $u$:

\begin{lstlisting}[language=Lean4]
instance : HasOpenTwo Proc Channel Channel Nat where
  open_ P u v k := (Proc.open (Proc.open P v (k + 1)) u k)
\end{lstlisting}

To complete the bidirectional infrastructure, \texttt{Proc.close} and \texttt{Channel.close} define the corresponding closing operation. Used primarily when abstracting explicit free names into new scopes, \texttt{Proc.close} traverses the process tree using a structural recursion identical to \texttt{Proc.open}, applying the exact same depth-incrementing rules for single and double binders. When the recursion reaches a leaf node, it delegates to \texttt{Channel.close}. If the leaf is a free channel (\texttt{FPName}), the function compares it against the target name $x$, upon a match, the explicit name is \emph{abstracted} into a bound De Bruijn index at the accumulated depth $k$:

\begin{lstlisting}[language=Lean4]
def Channel.close (u : Channel) (x : FPName) (k : Nat) : Channel :=
  match u with
  | .free name => if x == name then .bound k else .free name
  | .bound i   => .bound i
\end{lstlisting}

\paragraph{Local closure} \path{Processes/LocalClosure.lean}
defines local closure for processes as a two-parameter predicate \texttt{Proc.lc (k n~: Nat)~: Proc $\to$ Prop}. Because the calculus features a two-sorted syntax, the predicate must maintain independent depth counters: $k$ tracks the depth of channel binders, while $n$ tracks the depth of type binders. The type depth is needed when a process embeds a type, for instance as the payload of an output prefix, since the embedded type must be checked relative to the current type-binder depth.

The structural recursion evaluates each constructor by incrementing the appropriate depth counter according to the number and sort of binders introduced. Channel binders increase the channel depth $k$, while type binders increase the type depth $n$. For example, \texttt{tensor} binds a single continuation channel, incrementing the depth to $k+1$, whereas \texttt{cut} binds two dual endpoints simultaneously, incrementing the depth to $k+2$. Conversely, \texttt{input} binds a type variable, leaving $k$ unchanged while incrementing $n$ to $n+1$. Constructors introducing no binders, leave both counters unchanged:

\begin{lstlisting}[language=Lean4]
def Proc.lc : Nat -> Nat -> Proc -> Prop
  | _, _, .nil         => True
  | k, n, .one x P     => x.lc k /-$\land$-/ P.lc k n
  | k, n, .tensor x P  => x.lc k /-$\land$-/ P.lc (k + 1) n
  | k, n, .cut P       => P.lc (k + 2) n
  | k, n, .input x P   => x.lc k /-$\land$-/ P.lc k (n + 1)
  | ...
\end{lstlisting}

A process is considered globally \emph{closed} when it contains no dangling indices of either sort, meaning \texttt{Proc.lc 0 0} holds. This is registered as the abbreviation \texttt{Proc.lc\_0}.

\paragraph{Free names and freshness} \path{Processes/Names.lean} defines \texttt{Proc.f~: Proc $\to$ Finset FPName} to compute the free channel names of a process. The function traverses the syntax tree structurally, collecting all explicit free channel identifiers into a finite set. Since locally nameless binders are represented using anonymous indices, bound channels contribute nothing to this set.

For constructors carrying explicit subject channels, such as \texttt{tensor} and \texttt{link}, the free names of those channels are combined with the recursively computed free names of their continuations. Constructors without explicit channel identifiers of their own, such as \texttt{cut}, contribute only the free names recursively obtained from their continuations:

\begin{lstlisting}[language=Lean4]
def Proc.f : Proc -> Finset FPName
  | .cut P      => P.f
  | .par P Q    => P.f /-$\cup$-/ Q.f

  | .tensor x P => x.f /-$\cup$-/ P.f
  | .one x P    => x.f /-$\cup$-/ P.f
  | .nil        => {}
  | ...
\end{lstlisting}

The resulting finite set is used by \path{Processes/Fresh.lean} to generate names outside a forbidden context. Given a finite set $L$ of forbidden names, a fresh name is computed as $\max(L)+1$. The lemmas \texttt{exists\_one\_fresh} and \texttt{exists\_two\_fresh} guarantee one or two distinct names outside $L$, respectively. These lemmas provide witnesses for the co-finite quantification premises used throughout the typing and transition rules, in particular for restriction, where two fresh and distinct endpoints must be introduced simultaneously.

\paragraph{Substitution} The process syntax supports two substitution operations, reflecting its two-sorted binding structure. Name substitution is defined in \path{Processes/SubstNames.lean} as the function \texttt{Proc.substNames (R T~: FPName)~: Proc $\to$ Proc}, replacing all explicit free occurrences of the target name $T$ with the replacement name $R$. Since bound channels are represented by De Bruijn indices, name substitution only acts on explicit free channel leaves and leaves binders untouched. Consequently, the operation is capture-avoiding by construction and does not require $\alpha$-renaming or additional freshness side conditions.

Type substitution is defined in \path{Processes/SubstTypes.lean} as \texttt{Proc.substTypes (A~: Types) (k~: Nat)~: Proc $\to$ Proc}, substituting $A$ for the De Bruijn type index $k$ throughout a process. Whenever the traversal encounters an embedded type, such as the payload of an output prefix, it delegates to the type-level substitution operation \texttt{Types.subst}. When crossing an \texttt{input} prefix, which binds a type variable, the target depth is incremented and the substituted type is shifted, mirroring the binder case of \texttt{Types.subst} from \cref{subsubsec:stypes}:

\begin{lstlisting}[language=Lean4]
def Proc.substTypes (A : Types) (k : Nat) : Proc -> Proc
  | .input x P => .input x (P.substTypes (A.shift 0 1) (k + 1))
\end{lstlisting}

A consequence of this representation is that no analogous channel shifting operation, such as \texttt{shiftNames}, is required. In a pure De Bruijn encoding, variables are represented as relative indices and must be shifted when crossing binders. Free channels, however, are represented as global identifiers rather than relative positions, so their representation is unaffected by binder depth. This avoids structural adjustment of channel names during substitution and simplifies the process-level infrastructure.

\paragraph{Structural Properties} \path{Processes/Lemmas.lean} establishes the fundamental structural properties required by the later typing and operational metatheory. This includes commutation lemmas for interacting operations (e.g., \texttt{open\_substNames\_comm}, showing that opening commutes with name substitution), preservation properties for local closure (e.g., \texttt{lc\_of\_open}), and lemmas relating binders to free-name analysis (e.g., \texttt{f\_close}, proving that closing removes a free name from the resulting term).

Of particular importance are the commutation lemmas between opening and substitution: \texttt{open\_substNames\_comm} establishes that opening and name substitution commute, and the corresponding lemma for type substitution ensures that substituting under a binder 
produces the same result regardless of order. These properties are essential in the typability proof, where the co-finite witnesses produced by the typing rules must be reconciled with the concrete names introduced by the process transitions.

These results provide the core infrastructure required for the transition semantics developed in subsequent chapters.

\subsubsection{Environments}\label{subsubsec:environments}
Environments are defined in \path{Environment/Basic.lean} as 
\texttt{Env}, an abbreviation for a list of channel-type pairs:

\begin{lstlisting}[language=Lean4]
abbrev Elem := (FPName /-$\times$-/ Types)
abbrev Env  := List Elem
\end{lstlisting}

The choice of \texttt{List} as the underlying representation deserves explanation. Theoretical environments are unordered and duplicate-free, suggesting \texttt{Finset} as a natural implementation. However, since \texttt{Finset} is implemented as a quotient over lists, it complicates structural induction, pattern matching, and inversion over environments. This proved inconvenient in a development where typing derivations are frequently inverted and typing environments must be rearranged explicitly. A second attempt using association lists (\texttt{AList}) encountered similar proof-engineering difficulties. The final design therefore uses plain lists and recovers the unordered structure through an explicit permutation relation, trading quotient reasoning for structural induction and simpler interaction with Lean's tactic machinery.

\paragraph{Recovering the PCM structure} Merging two environments is implemented as list concatenation, making it a simple structural, but total, function:

\begin{lstlisting}[language=Lean4]
abbrev Env.merge (/-$\Gamma~\Delta$-/ : Env) : Env := /-$\Gamma$-/ ++ /-$\Delta$-/
infixl:69 "/-$,$-/" => Env.merge  -- uses \glq to avoid clashing with the actual comma
\end{lstlisting}

Because lists do not naturally form a Partial Commutative Monoid (PCM) but are associative by definition, we only need to formally recover commutativity. 

Since list concatenation is associative definitionally but not commutative, the commutative structure of environments is recovered by reasoning up to permutation. This is achieved using Lean's built-in \texttt{List.Perm} relation, instantiated through a custom \texttt{HasPerm} typeclass and denoted by the infix relation \hl{$\thl{\Gamma \sim \Delta}$}. 

The essential monoidal laws, including commutativity, associativity, and left and right identity for $\thl{\emptyhyp}$,\footnote{Using $\thl{\emptyhyp}$ rather than the literal \texttt{[]} requires explicit rewrite lemmas for terms such as $\thl{\envmerge{\emptyhyp}{\Gamma}}$. If \texttt{[]} were used directly, $\thl{\envmerge{[]}{\Gamma}}$ would reduce by definitional equality, since \texttt{Env.merge} abbreviates \texttt{List.append}.} are established as:

\begin{lstlisting}[language=Lean4]
lemma Env.merge_comm (/-$\Gamma~\Delta$-/ : Env) : /-$\perm{\envmerge{\Gamma}{\Delta}}{\envmerge{\Delta}{\Gamma}}$-/
lemma Env.merge_assoc (/-$\Gamma~\Delta~\Xi$-/ : Env) : /-$\envmerge{\Gamma}{}\envmerge{\Delta}{\Xi}$-/ = /-$\envmerge{\Gamma}{}$($\envmerge{\Delta}{\Xi}$)-/
\end{lstlisting}

% Additionally, we use \hl{$\thl{\emptyhyp}$} as unit for merging and implement identity for merging it on both the left and right side of an environment as well as some useful lemmas for defining a standard representation for example turning \hl{$\thl{e :: \emptyhyp}$ into $\thl{[e]}$}.

% \begin{remark}
%   \begin{highlight}  
%     The use of $\thl{\emptyhyp}$ as unit has necessitated explicit lemmas to rewrite and reduce terms such as $\thl{\envmerge{\emptyhyp}{\Gamma} \text{ to } \Gamma}$. Whereas if $\thl{[]}$ were used as unit terms like $\thl{\envmerge{[]}{\Gamma}}$ would reduce by definitional equality, because the \texttt{Env.merge} notation is an abbreviation for \texttt{List.append}, Lean can see through it and reduce automatically.
%   \end{highlight}
% \end{remark}

The partiality of environment merging is enforced by explicit predicates rather than by making \texttt{Env.merge} a partial function. \texttt{Env.names} extracts the domain as a \texttt{Finset}, enabling Lean's built-in \texttt{Disjoint} typeclass. Internal linearity (no channel typed twice) is enforced by \texttt{Env.Nodup}:

\begin{lstlisting}[language=Lean4]
def Env.names (/-$\Gamma$-/ : Env) : Finset FPName := (/-$\Gamma$-/.map Prod.fst).toFinset 
def Env.disjoint (/-$\Gamma~\Delta$-/ : Env) : Prop := Disjoint /-$\Gamma$-/.names /-$\Delta$-/.names
def Env.Nodup (/-$\Gamma$-/ : Env) : Prop := (/-$\Gamma$-/.map Prod.fst).Nodup
\end{lstlisting}

The relationship between linearity, disjointness, and merging of typing environments is captured by \texttt{Env.Nodup\_merge\_iff}, which states that a merged environment is linear if and only if both component environments are individually linear and mutually disjoint.

\paragraph{Server usability} The typing rule for server replication requires all dependency channels to carry exponential request types. This side condition is captured by \texttt{Env.serverUsable}, which asserts that every type in an environment satisfies \texttt{Types.isServerUsable}, i.e.\ has the form \hl{$\thl{\query B}$}.

\begin{lstlisting}[language=Lean4]
def Env.serverUsable (/-$\Gamma$-/ : Env) : Prop :=
  /-$\forall$-/p, p /-$\in~\Gamma$-/ -> p.snd.isServerUsable
prefix:max "?/-$_e$-/" => Env.serverUsable
\end{lstlisting}

\paragraph{Lifted operations} Since environments contain types, the locally nameless operations from \cref{subsubsec:stypes} are lifted pointwise over the type component of each \texttt{Elem}. Local closure, type shifting, name substitution, and type substitution are all defined by mapping over the list. The file \path{Environment/Lemmas.lean} proves that these operations preserve the names, disjointness, nodup, and permutation properties of environments.

The full definitions and lemmas are listed in \cref{app:environments}. %FIXME: make and references appendix

\subsubsection{Hyperenvironments}\label{subsubsec:hyperenvironments} Hyperenvironments are defined in \path{HyperEnvironment/Basic.lean} as \texttt{HyperEnv}, an abbreviation for a list of environments:

\begin{lstlisting}[language=Lean4]
abbrev HyperEnv := List Env
\end{lstlisting}

As for environments, merging is implemented as list concatenation, using \hl{$\thl{\emptyhyp}$} as the unit and \hl{$\thl{\hypermerge{\hyp{G}}{\hyp{H}}}$} as notation for composition. Associativity and unit laws therefore follow from the underlying list structure. However, recovering the commutative structure requires more than the ordinary list permutation relation, since hyperenvironments are lists whose elements are themselves environments considered modulo permutation.

\paragraph{Deep permutation} 
For environments, Lean's \texttt{List.Perm} relation is sufficient, since it allows arbitrary reordering of channel-type pairs. For hyperenvironments, however, permutation must operate at two levels: it must allow reordering of component environments, and it must also respect permutation equivalence inside each component environment.

For example, consider the hyperenvironment containing a single component environment \hl{$\thl{[\cht{x}{A}, \cht{y}{B}]}$}. Ordinary \texttt{List.Perm} treats this component environment as an opaque element, so it does not identify it with \hl{$\thl{[\cht{y}{B}, \cht{x}{A}]}$}. The custom relation \texttt{HyperEnv.Perm} instead permits component environments to be replaced by permutation-equivalent environments.

% \begin{example}
%   \begin{highlight}
%     Consider the hyperenvironment $\thl{[\cht{x}{A}, \cht{y}{B}]}$, consisting of a single environment with two channel-type pairs. Under \texttt{List.Perm}, this would \emph{not} be equivalent to $\thl{[\cht{y}{B}, \cht{x}{A}]}$, since the single environment element is treated as an opaque value. Under \texttt{HyperEnv.Perm}, the \texttt{cons} constructor permits the head environment to be replaced by any permutation-equivalent environment, so $\thl{[\cht{x}{A}, \cht{y}{B}] \sim [\cht{y}{B}, \cht{x}{A}]}$ holds via \texttt{cons} with the environment permutation $\thl{\cht{x}{A}, \cht{y}{B} \sim \cht{y}{B},\cht{x}{A}}$.
%   \end{highlight}
% \end{example}

\begin{lstlisting}[language=Lean4]
inductive HyperEnv.Perm : HyperEnv -> HyperEnv -> Prop where
  | nil  : Perm [] []
  | cons : {/-$\Gamma~\Delta$-/ : Env} {/-$\hyp{G~H}$-/ : HyperEnv} : /-$\perm{\Gamma}{\Delta}$-/ -> Perm /-$\hyp{G}~\hyp{H}$-/ -> Perm (/-$\Gamma :: \hyp{G}$-/) (/-$\Delta :: \hyp{H}$-/)
  | swap : {/-$\Gamma~\Delta$-/ : Env} {/-$\hyp{G}$-/ : HyperEnv} : Perm (/-$\Gamma :: \Delta :: \hyp{G}$-/) (/-$\Delta :: \Gamma :: \hyp{G}$-/)
  | trans {/-$\hyp{G~H~J}$-/ : HyperEnv} : Perm /-$\hyp{G~H}$-/ -> Perm /-$\hyp{H~J}$-/ -> Perm /-$\hyp{G~J}$-/
\end{lstlisting}

The key constructor is \texttt{cons}. Unlike ordinary list permutation, it does not require the head environments to be syntactically identical, it only requires them to be permutation-equivalent. Thus \texttt{HyperEnv.Perm} is a deep permutation relation, propagating equivalence both across the ordering of component environments and within the environments themselves.

\paragraph{Well-formedness} Hyperenvironment well-formedness is decomposed into two predicates. The predicate \texttt{HyperEnv.Nodup} requires each component environment to be internally linear, while \texttt{HyperEnv.PairwiseDisjoint} requires distinct component environments to have disjoint domains:

\begin{lstlisting}[language=Lean4]
def HyperEnv.Nodup (/-$\hyp{G}$-/ : HyperEnv) : Prop :=
  /-$\forall~\Gamma, ~\Gamma \in \hyp{G}$-/ -> Env.Nodup /-$\Gamma$-/

def HyperEnv.PairwiseDisjoint (/-$\hyp{G}$-/ : HyperEnv) : Prop :=
  List.Pairwise Env.disjoint /-$\hyp{G}$-/
\end{lstlisting}

The distinction is important because the two predicates rule out different violations of linearity. For example, assuming $x$, $y$, and $z$ are distinct names:

\begin{highlight}  
  \begin{itemize}
    \item $\thl{\hypermerge{[\cht{x}{A}]}{[\cht{y}{B}, \cht{z}{C}]}}$ satisfies both predicates.
    \item $\thl{\hypermerge{[\cht{x}{A}, \cht{x}{B}]}{[\cht{y}{C}]}}$ violates \texttt{Nodup}, since $x$ appears twice within one component environment.
    \item $\thl{\hypermerge{[\cht{x}{A}]}{[\cht{x}{B}, \cht{y}{C}]}}$ violates \texttt{PairwiseDisjoint}, since $x$ appears in two distinct components.
  \end{itemize}
\end{highlight}
  
Together, these predicates enforce global linearity: every channel appears at most once across the whole hyperenvironment.

\paragraph{Lifted operations} 
As with environments, type shifting, name substitution, and type substitution are lifted pointwise over the list of component environments. The file \path{HyperEnvironment/Lemmas/Basic.lean} proves that these operations preserve names, disjointness, pairwise disjointness, and the deep permutation relation. For example, preservation of permutation under shifting is proved by induction on \texttt{HyperEnv.Perm}, using the corresponding environment-level permutation lemma in the \texttt{cons} case.

The full definitions and lemmas are listed in \cref{app:hyperenvironments}.

\subsubsection{Typing Judgements}\label{subsubsec:judgements}
The typing relation is defined in \path{Judgement/Basic.lean} as the inductive predicate \texttt{Typing}:

\begin{lstlisting}[language=Lean4]
inductive Typing : Nat -> Proc -> HyperEnv -> Prop
\end{lstlisting}

We write \hl{$\judge{n}{P}{\hyp{G}}$} for a derivation of this predicate. The index $n$ tracks the current type-binder depth, while the remaining indices record the process being typed and its associated typing environment. This intrinsic indexing is later used by the erasure maps in the semantics and metatheory.

\paragraph{Type-depth indexing}
The type-depth index is relevant whenever the derivation crosses a polymorphic binder. For example, the \texttt{forall\_} constructor increments the depth from $n$ to $n+1$ and shifts the surrounding environment to keep embedded type indices in scope:

\begin{lstlisting}[language=Lean4]
| forall_ :
    Typing (n + 1) P [/-$\cht{\texttt{x}}{\texttt{B}} :: \Gamma^{+}$-/] ->
    Typing n (#x/-$\dparenL\diamond\dparenR$-/.P) [/-$\cht{\texttt{x}}{\forall.\texttt{B}} :: \Gamma$-/]
\end{lstlisting}

The shift \hl{$\thl{\typeshiftsingle{\Gamma}}$} abbreviates shifting the type indices in $\Gamma$ by one, mirroring the binder-sensitive shifting used by type substitution in \cref{subsubsec:stypes}.

\paragraph{Exchange and explicit side conditions}
Because environments and hyperenvironments are represented as lists, the unordered and partial structure of the theoretical hyperenvironment is recovered explicitly. The typing relation includes exchange rules for reasoning up to permutation equivalence:

\begin{lstlisting}[language=Lean4]

\end{lstlisting}

The exchange rules recover the unordered character of the paper presentation without quotienting environments or hyperenvironments. The complementary issue is partiality: although merging is implemented as total list concatenation, typing rules carry explicit disjointness and freshness premises to ensure that only valid linear compositions are formed. For example, \texttt{mix} requires the two hyperenvironments to be disjoint, while prefix rules such as \texttt{tensor} and \texttt{parr} require freshness premises ensuring that subject channels do not already appear in the continuation environment.

The same design principle reappears later in the operational semantics, where transitions must also respect permutation equivalence of environments and hyperenvironments.

\begin{highlight}

\judge{n}{P}{\hyp{G}} \implies \phl{P}.f = \thl{\hyp{G}}.names
\]
\end{highlight}

This ensures exact correspondence between process free names and typed environment entries: no free process channel is left untyped, and no environment entry is unused.

Building on this, \path{Judgement/Linearity.lean} proves \texttt{Typing\_preserves\_disjointness}: any well-typed hyperenvironment is pairwise disjoint. Together these results guarantee that typing derivations can only be constructed for well-formed, linear contexts.

\subsection{Semantics}\label{subsec:semantics}
The dynamic behaviour of the \pimll{} fragment is formalised in the \path{Semantics/} namespace. Following the erasure structure described in \cref{subsec:operational-semantics}, the development contains three related transition systems: a typed transition system over typing derivations, and two projected systems describing the induced process and environment behaviour.

\begin{itemize}
    \item \textbf{\texttt{TypingStep}$_\texttt{m}$}: the primary, resource-aware LTS over typing derivations (\path{JudgementStep/Basic.lean});
    \item \textbf{\texttt{ProcStep}$_\texttt{m}$}: the process-level LTS obtained by forgetting typing resources (\path{ProcStep/Basic.lean});
    \item \textbf{\texttt{EnvStep}$_\texttt{m}$}: the resource-level LTS describing the corresponding evolution of hyperenvironments (\path{EnvStep/Basic.lean}).
\end{itemize}

\paragraph{Labels}\label{subsubsec:labels}
Transition labels are formalised in \path{Labels.lean}. Although the operational semantics mechanised here target \pimll{}, the underlying action vocabulary is defined for the full \pill{} calculus to support future extensions.

The core action type, \texttt{Act}, captures observable communication events, including empty communication, channel transmission, type instantiation, and server interaction. Selection and server actions are parameterised by the auxiliary datatype \texttt{Mu}. The \texttt{Lbl} inductive then extends observable actions with the silent transition $\tau$, explicit session-link labels, and a parallel constructor combining two observable actions directly, reflecting the synchronized action labels used by the parallel rules.

\begin{lstlisting}[language=Lean4]
inductive Act : Type
  | one       (x : FPName)
  | tensor    (x y : FPName)
  | output    (x : FPName) (A : Types)
  | muBrack   (x : FPName) (/-$\mu$-/ : Mu)
  | ...

inductive Lbl : Type
  | tau
  | link  (x y : FPName)
  | act   (p : Act)
  | par   (l l' : Act)
\end{lstlisting}

Each label defines computable sets of free names (\texttt{Lbl.f}) and introduced names (\texttt{Lbl.i}), which are used in the side conditions for the \cref{rule:pill-mix-1,rule:pill-proc-mix-2,rule:pill-mix-sync}. To preserve alignment with the theoretical presentation, we use the \texttt{HasBracket} and \texttt{HasParen} typeclasses for \texttt{Act} and \texttt{Lbl} to allow the notation for process prefixes to be reused uniformly for labels as well. For instance, $\dlsend{x}{y}$ denotes both the output process prefix and the corresponding output label.

\subsubsection{The Typed Transition System}\label{subsubsec:judgementstep}
The primary LTS, \texttt{TypingStep}$_\texttt{m}$, is a relation between typing derivations. Its constructors mirror the operational rules shown in \cref{fig:mpill-sos}, but make the type-theoretic content of each step explicit: every transition carries a typing derivation as its source and produces a typing derivation as its target. The system is therefore intrinsically typed.

\begin{lstlisting}[language=Lean4]
inductive TypingStep/-$_\texttt{m}$-/ : 
  {n : Nat} /-$\to$-/ {/-$\hyp{G}$-/ : HyperEnv} /-$\to$-/ {P : Proc} /-$\to$-/ Typing n P /-$\hyp{G}$-/ /-$\to$-/ 
  Lbl /-$\to$-/ {n' : Nat} /-$\to$-/ {/-$\hyp{G}$-/' : HyperEnv} /-$\to$-/ {P' : Proc} /-$\to$-/ Typing n' P' /-$\hyp{G}$-/' /-$\to$-/ Prop
\end{lstlisting}

As established previously, both environment and hyperenvironment composition are formalised using total list appends. Consequently, the explicit disjointness proofs required by the static \texttt{Typing} relation to safely mix environments must propagate directly into the dynamic \texttt{TypingStep}$_\texttt{m}$ relation. For instance, the \texttt{par$_1$} constructor requires explicit hypotheses (\texttt{hD1} and \texttt{hD2}) to guarantee that the hyperenvironments remain strictly disjoint both before and after the transition:

\begin{lstlisting}[language=Lean4]
| par/-$_1$-/
    (hD1 : /-$\hyp{G}$-/.disjoint /-$\hyp{H}$-/) (hD2 : /-$\hyp{G}$-/'.disjoint /-$\hyp{H}$-/)
    (h : TypingStep/-$_\texttt{m}$-/ /-$\der{D}$-/ l /-$\der{D}$-/')
    (disj : l.i /-$\cap$-/ Q.f = /-$\emptyhyp$-/) :
    TypingStep/-$_\texttt{m}$-/
      (Typing.mix hD1 /-$\der{D}$-/ /-$\der{E}$-/)
      l
      (Typing.mix hD2 /-$\der{D}$-/' /-$\der{E}$-/)
\end{lstlisting}

% \begin{remark}
%   The inclusion of \texttt{hD2} to track post-state disjointness was to simplify induction, but is not strictly necessary as this is a derivable fact stemming from the pre-state disjointness (\texttt{hD1}) and the freshness condition $i(l) \cap Q.f = \emptyset$. Combining \texttt{Typing\_f\_eq\_names} and \texttt{hD1}, we can establish that $(P.f \cup i(l)) \cap Q.f = \emptyset$. Combining this with a structural property of the TypingStep relation stating $\hyp{G}' \subseteq \hyp{G} \cup i(l)$, we can deduce that $\hyp{G}' \cap Q.f = \emptyset$. By rewriting this using \texttt{Typing\_f\_eq\_names}, we obtain the required post-state disjointness \texttt{hD2}.

% \end{remark}

The post-state disjointness proof \texttt{hD2} is included explicitly as a convenience: while it is derivable from \texttt{hD1}, the freshness condition $i(l) \cap Q.f = \emptyset$, and the structural property that transitions only introduce names recorded by their label, keeping it as a premise avoids reconstructing this fact repeatedly in later proofs.

\begin{remark}
Strictly stepping typing derivations can expose structural artifacts that are usually hidden in the paper presentation. For example, in \cref{fig:cut-unit-trans}, the intermediate derivation is typed by $\thl{\emptyhyp \pp \cht{y}{1}}$ rather than simply $\thl{\cht{y}{1}}$, because the \rname{Mix} rule preserves the empty component contributed by the terminated left process. In Lean, this corresponds to a \texttt{Typing.mix} constructor containing a \texttt{Typing.mix\_0} sub-derivation. The result is valid, but reducing it to the canonical form requires applying the monoidal identity laws of the hyperenvironment explicitly, rather than by definitional equality. The final $\equiv$ step in the figure, which additionally uses process congruence to identify $\phl{\nil \pp \nil}$ with $\phl{\nil}$, is not currently automated because structural congruence has not been mechanised. This limitation is discussed further in \cref{sec:discussion}.
\end{remark}

\subsubsection{Projected Transition Systems}\label{subsubsec:inducedlts}
The process and environment transition systems are defined to capture the two erasure views of a typed transition. \texttt{ProcStep}$_\texttt{m}$ records the process behaviour obtained by forgetting typing resources, while \texttt{EnvStep}$_\texttt{m}$ records the corresponding resource evolution. These relations are later connected to \texttt{TypingStep}$_\texttt{m}$ by the simulation theorems in \cref{subsec:session-fidelity}.

% While \texttt{TypingStep}$_\texttt{m}$ defines the complete, resource-aware dynamics of the calculus, extracting the independent process and environment LTSs is mathematically necessary to demonstrate that the linear type system is sound with respect to the underlying untyped semantics. 

% By projecting the complete typing derivations into these independent transition systems, the formalisation reproduces the paper's erasure properties. 

% Consequently, these projected relations not only fulfill the theoretical requirements of the calculus, but also serve the practical purpose of separating concerns, thereby keeping the mechanised simulation proofs tractable.

\paragraph{Process steps}
\texttt{ProcStep}$_\texttt{m}$ models the syntactic evolution of processes independently of typing resources. Unlike the typing relation, it is not indexed by a typing derivation and therefore does not use co-finite premises. Binder-opening rules instead choose concrete fresh names directly and record the required freshness as explicit side conditions. For example, the \texttt{tensor} rule opens the continuation with a concrete name $y$, requiring $y$ to be fresh for both the subject channel and the continuation:

\begin{lstlisting}[language=Lean4]
  | tensor {P : Proc} {x y : FPName} (hF : y /-$\notin$-/ {x} /-$\cup$-/ P.f) :
      ProcStep/-$_\texttt{m}$-/ (/-$\dsend{\texttt{\#x}}{\bullet}{\texttt{P}}$-/) (/-$\dlsend{\texttt{x}}{\texttt{y}}$-/) /-$\dopen{\texttt{P}}{\texttt{\#y}}$-/
\end{lstlisting}

This creates a mismatch with the co-finite formulation of the typing rules. Thus \texttt{ProcStep}$_\texttt{m}$ remains close to a standard concrete transition relation, while the additional freshness reconciliation is handled in the typability proof. A co-finite formulation of \texttt{ProcStep}$_\texttt{m}$ would align more directly with the typing rules, but the present formulation keeps the erased LTS closer to a standard concrete transition relation.

\paragraph{Environment steps}
The structural evolution of hyperenvironments, written $\thl{\hyp{G}} \xrightarrow{l} \thl{\hyp{H}}$, is formalised by \texttt{EnvStep}$_\texttt{m}$. Unlike the typed transition system, \texttt{EnvStep}$_\texttt{m}$ deliberately contains only the resource transformation described by the label. It does not independently enforce all disjointness and well-formedness conditions. Those properties are supplied by the typing derivation in \texttt{TypingStep}$_\texttt{m}$.

This separation keeps the projected resource semantics lightweight. The environment relation describes how resources change, while the typed semantics proves that these changes occur from well-formed linear contexts.

The following metatheory shows that these transition systems agree: typed transitions project to process and environment transitions, and process transitions from well-typed states can be lifted back to typed transitions.
