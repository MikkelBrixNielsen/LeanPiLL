\section{Formalisation}\label{sec:formalisation}
This section describes the mechanisation of \pill{} in Lean 4, bridging the theoretical foundations developed in~\cref{sec:background,sec:binding-architecture} and their concrete implementation. The formalisation is organised into three top-level namespaces: \texttt{PiLL.Model}, which defines the static structure of the calculus, \texttt{PiLL.Semantics}, which defines its operational behaviour, and \texttt{PiLL.SessionFidelity}, which establishes the metatheoretic results connecting the two. Each component is presented in dependency order, highlighting design decisions and divergences from~\citet{abs-2106-11818}.

\subsection{Model}\label{subsec:model}
The \texttt{Model} namespace covers the full \pill{} calculus and is structured around the layers introduced in~\cref{sec:background}. \texttt{Base.lean} provides shared syntactic infrastructure used across the model. Session types are defined in \texttt{STypes/}, processes in \texttt{Processes/}, and typing contexts in \texttt{Environments/} and \texttt{HyperEnvironment/}. Typing judgements and their properties are collected in \texttt{Judgement/}, which includes inversion lemmas, linearity properties, substitution, and the co-finite freshness infrastructure described in~\cref{subsec:co-finite-quantification}.

\subsubsection{Session Types}\label{subsubsec:stypes}
Session types are defined in \texttt{STypes/Basic.lean} as the inductive datatype \texttt{Types}. Following the locally nameless syntax established in \cref{subsec:locally-nameless}, type variables are isolated into a separate inductive type, \texttt{TVar}, which explicitly distinguishes between free and bound occurrences:
%
\begin{lstlisting}[language=Lean4]
inductive TVar : Type
  | free  (x : FTVar)   
  | bound (x : BTVar)   
\end{lstlisting}
%
Here, \texttt{FTVar} represents a free type variable identified by a natural number, while \texttt{BTVar} represents a bound type variable encoded as a De Bruijn index.

The remaining constructors directly mirror the theoretical grammar of the calculus. In addition, the formalisation introduces constructors for uninterpreted atomic base types (\texttt{atom} and \texttt{atomDual}), which provide the base cases for the inductive structure of the syntax. \Cref{tab:types-comparison} illustrates the correspondence between the paper syntax, the locally nameless representation, and the Lean implementation.

  | .forall_ A   => .exists_ (dual A)
  | .one         => .bot
  | ...
\end{lstlisting}

\paragraph{Local closure} \texttt{STypes\slash{}Properties.lean} defines local closure for types as a depth-indexed predicate \texttt{Types.lc (k~: Nat)~: Types $\to$ Prop}, where the depth parameter $k$ tracks how many binders the recursion has traversed. 

At the leaves of the syntax tree, local closure is evaluated by the helper predicate \texttt{TVar.lc}. Because free variables are explicit they do not contain any indices, as such they are inherently locally closed at any depth. Conversely, a bound variable is only locally closed if its De Bruijn index $i$ is strictly less than the current depth $k$, ensuring it points to an enclosing scope:

\begin{lstlisting}[language=Lean4]
def TVar.lc : Nat -> TVar -> Prop
  | _, .free _   => True
  | k, .bound i  => i < k
\end{lstlisting}

The primary \texttt{Types.lc} predicate is then defined by structural recursion. For non-binding constructors, the depth parameter distributes across the sub-terms. When a variable is encountered, the predicate delegates the check to \texttt{TVar.lc}. When descending into the body of a polymorphic binder, the depth counter increments by one, bringing the newly introduced index safely into scope:

\begin{lstlisting}[language=Lean4]
def Types.lc : Nat -> Types -> Prop
  | _, .one         => True
  | k, .var v       => TVar.lc k v
  | k, .tensor A B  => A.lc k '$\land$' B.lc k
  | k, .forall_ A   => A.lc (k + 1)
  | k, .exists_ A   => A.lc (k + 1)
  | ...
\end{lstlisting}

Finally, a type is defined as \emph{closed} if it contains no dangling indices at the top level, meaning it is locally closed at depth $0$. This is registered as the abbreviation \texttt{Types.lc\_0}.

\paragraph{Shifting} \path{STypes/Shift.lean} defines shifting following the standard De Bruijn shifting operation introduced in \cref{subsec:co-finite-quantification}. The operation traverses the syntax tree structurally using a cutoff depth $d$ and a shift amount $c$.

For standard connectives, shifting distributes recursively across subterms, while base constructors such as \texttt{one} and \texttt{bot} remain unchanged. When traversing a polymorphic binder like \texttt{forall\_}, the cutoff depth increments by one to account for the newly entered scope:

\begin{lstlisting}[language=Lean4]
def Types.shift (d c : Nat) : Types -> Types
  | .var v       => .var (v.shift d c)
  | .tensor A B  => .tensor (A.shift d c) (B.shift d c)
  | .forall_ A   => .forall_ (A.shift (d + 1) c)
  | t            => t
\end{lstlisting}

At the variable level, free variables remain unchanged. For bound indices, the function compares the De Bruijn index $i$ against the cutoff depth $d$. Indices satisfying $i < d$ are locally bound within the traversed scope and therefore remain unchanged. Otherwise, the index is incremented by $c$ to preserve its reference to the surrounding environment:

\begin{lstlisting}[language=Lean4]
def TVar.shift (d c : Nat) : TVar -> TVar
  | .bound i => if i < d then .bound i else .bound (i + c)
  | .free n  => .free n
\end{lstlisting}

\paragraph{Substitution} \path{STypes/Subst.lean} defines substitution as the eager substitution of $A$ for a target De Bruijn index $k$ within a host type $B$, denoted as $B\{A // k\}$. 

At the variable level, the function evaluates the bound De Bruijn index $i$ against the target depth $k$. If $i = k$, the target has been reached, and the variable is replaced by the instantiated type $A$. If $i < k$, the variable is bound by an inner scope and is unaffected. Finally, if $i > k$, the index refers to an outer binder beyond the substituted variable. Since substitution removes the binder corresponding to $k$, these indices are decremented by one to preserve their relative distance to the surrounding environment.

\begin{lstlisting}[language=Lean4]
def Types.subst (B A : Types) (k : Nat) : Types :=
  match B with
  | .var (.bound i) =>
      if i == k then A
      else if i > k then .var (.bound (i - 1))
      else .var (.bound i)
\end{lstlisting}

This operation is lifted to the \texttt{Types} level via structural recursion. For standard connectives, the substitution simply distributes across the sub-terms. However, when descending into a polymorphic binder such as \texttt{forall\_}, two critical protective adjustments must occur. First, the target depth $k$ increments by one ($k + 1$) to account for crossing the new binder. Second, the payload type $A$ is explicitly shifted (\texttt{shift 0 1 A}) to ensure that any free variables residing inside $A$ are not accidentally captured by this newly entered scope:

\begin{lstlisting}[language=Lean4]
  | .forall_ B => .forall_ (B.subst (shift 0 1 A) (k + 1))
\end{lstlisting}

\paragraph{Notation} \path{STypes/Notation.lean} defines notation following the mathematical conventions established in \cref{subsec:types} and extended in \nameref{par:ln-syntax-types}. The only noteworthy divergence is that the exponentials \hl{$\thl{\bang A}$} and \hl{$\thl{\query A}$} are written \hl{$\thl{\bang\bang A}$} and \hl{$\thl{\query\query A}$} respectively, to avoid clashing with Lean's built-in $\bang$ (boolean negation) and $\query$ (syntactic hole) operators.

\subsubsection{Processes}\label{subsubsec:processes}
Processes are defined in \path{Processes/Basic.lean} as the inductive type \texttt{Proc}. Following the established locally nameless architecture, channel references are partitioned into a dedicated \texttt{Channel} inductive. Explicit free channels are instantiated as concrete natural numbers (\texttt{FPName}). While the raw process syntax permits arbitrary reuse of these numbers, using \texttt{Nat} allows the formalisation to systematically compute strictly fresh names by incrementing the supremum of any finite set of existing names (mechanised in \path{Processes/Fresh.lean}). Conversely, bound channels are represented using De Bruijn indices, encoding their relative distance to the corresponding binder.

\begin{lstlisting}[language=Lean4]
inductive Channel : Type where
  | free  (x : FPName)
  | bound (x : BPName)
\end{lstlisting}

% FIXME: Phrasing of the last sentence
As discussed in \cref{subsec:locally-nameless}, binding constructs in the process syntax no longer carry explicit payload variables. Instead, bound occurrences are captured purely by their relative position. Comparing the standard paper grammar with the intermediate locally nameless notation and the final constructors of the \texttt{inductive Proc} type illustrates this abstraction:

\begin{highlight}  
\begin{center}
\begin{tabular}{llll}
    \toprule
    \textbf{Standard} & \textbf{Locally Nameless} & \textbf{Lean Constructor} & \textbf{Binds} \\
    \midrule
    $\phl{\send{x}{y}{P}}$ & $\phl{\send{x}{\bullet}{P}}$ & \texttt{| tensor (x~: Channel) (P~: Proc)} & 1 channel \\
    $\phl{\recv{x}{y}{P}}$ & $\phl{\recv{x}{\bullet}{P}}$ & \texttt{| parr (x~: Channel) (P~: Proc)} & 1 channel \\
    $\phl{\res{xy}{P}}$ & $\phl{\res{(\bullet, \bullet)}{P}}$ & \texttt{| cut (P~: Proc)} & 2 channels \\
    $\phl{\recvtype{x}{X}{P}}$& $\phl{x(\diamond).P}$ & \texttt{| input (x~: Channel) (P~: Proc)} & 1 type \\
    $\phl{\clientdup{x}{x'}{P}}$ & $\phl{\clientdup{x}{\bullet}{P}}$ & \texttt{| duplicate (x~: Channel) (P~: Proc)} & 1 channel \\
    \bottomrule
\end{tabular}
\end{center}
\end{highlight} 

Notice that \texttt{cut} takes only a continuation \hl{$\phl{P}$} with no explicit channel arguments, as both dual endpoints are simultaneously bound as indices $0$ and $1$ within the scope of \hl{$\phl{P}$}. Similarly, for constructs like \texttt{tensor}, \texttt{parr}, and \texttt{input}, the subject channel $x$ over which the interaction occurs is kept explicit, while the transmitted payload is anonymized into the continuation.

\paragraph{Opening and closing} \path{Processes/OpenClose.lean} defines opening and closing operations following the Locally Nameless principles established in \cref{subsec:opening-and-closing}. 

Because binders are represented positionally, the depth parameter $k$ increments according to the number of channels bound by each constructor. For standard communication prefixes like \texttt{tensor}, \texttt{parr}, and the server \texttt{duplicate} operation, exactly one channel is bound, incrementing $k$ by one. The restriction constructor (\texttt{cut}) simultaneously binds two dual endpoints, requiring $k$ to increment by two. Notably, the \texttt{input} constructor binds a type variable rather than a channel. Consequently, it does not affect the channel depth parameter $k$.

\begin{lstlisting}[language=Lean4]
def Proc.open (P : Proc) (u : Channel) (k : Nat) : Proc :=
  match P with
  | .tensor x P     => .tensor (x.open u k) (P.open u (k + 1))  
  | .parr   x P     => .parr   (x.open u k) (P.open u (k + 1))  
  | .cut      P     => .cut                 (P.open u (k + 2))
  | .input  x P     => .input  (x.open u k) (P.open u k)
  | ...
\end{lstlisting}

At the leaves of the syntax tree, this recursive traversal delegates to the base case defined by \texttt{Channel.open}. For bound channels, the function evaluates the De Bruijn index $i$ against the target depth $k$, replacing it with the instantiated channel $v$ upon an exact match. Explicit free channels remain entirely unaffected:

\begin{lstlisting}[language=Lean4]
def Channel.open (u v : Channel) (k : Nat) : Channel :=
  match u with
  | bound i => if i == k then v else bound i
  | c => c
\end{lstlisting}

For restriction, which requires instantiating two endpoints simultaneously, the \texttt{HasOpenTwo} typeclass from \path{Base.lean} is instantiated by opening sequentially: first replacing index $k+1$ with the second endpoint $v$, then replacing index $k$ with the first endpoint $u$:

\begin{lstlisting}[language=Lean4]
instance : HasOpenTwo Proc Channel Channel Nat where
  open_ P u v k := (Proc.open (Proc.open P v (k + 1)) u k)
\end{lstlisting}

To complete the bidirectional infrastructure, \texttt{Proc.close} and \texttt{Channel.close} define the exact inverse operation. Used primarily when abstracting explicit free names into new scopes, \texttt{Proc.close} traverses the process tree using a structural recursion identical to \texttt{Proc.open}, applying the exact same depth-incrementing rules for single and double binders. When the recursion reaches a leaf node, it delegates to \texttt{Channel.close}. If the leaf is a free channel (\texttt{FPName}), the function compares it against the target name $x$, upon a match, the explicit name is \emph{abstracted} into a bound De Bruijn index at the accumulated depth $k$:

\begin{lstlisting}[language=Lean4]
def Channel.close (u : Channel) (x : FPName) (k : Nat) : Channel :=
  match u with
  | .free name => if x == name then .bound k else .free name
  | .bound i   => .bound i
\end{lstlisting}

\paragraph{Local closure} \path{Processes/LocalClosure.lean}
defines local closure for processes as a two-parameter predicate \texttt{Proc.lc (k n~: Nat)~: Proc $\to$ Prop}. Because the calculus features a two-sorted syntax, the predicate must maintain independent depth counters: $k$ tracks the depth of channel binders, while $n$ tracks the depth of type binders. This ensures that when a process embeds a type, such as the payload $A$ in an output operation, the embedded type can be correctly evaluated against the current type depth $n$ during its own local closure check.

The structural recursion evaluates each constructor by incrementing the appropriate counter based on the number and sort of binders introduced. For instance, a \texttt{tensor} prefix binds a single continuation channel, incrementing the channel depth to $k+1$. The restriction operation (\texttt{cut}) binds two dual endpoints simultaneously, incrementing the depth to $k+2$. Conversely, an \texttt{input} prefix binds a polymorphic type variable rather than a channel. This leaves the channel depth $k$ unchanged while incrementing the type depth to $n+1$, while non-binders, like \texttt{one} increment neither $n$ nor $k$, and the terminated process is trivially locally closed:

The structural recursion evaluates each constructor by incrementing the appropriate depth counter according to number and sort of binders introduced. Channel binders increase the channel depth $k$, while type binders increase the type depth $n$. For example, \texttt{tensor} binds a single continuation channel, incrementing the depth to $k+1$, whereas \texttt{cut} binds two dual endpoints simultaneously, incrementing the depth to $k+2$. Conversely, \texttt{input} binds a type variable, leaving $k$ unchanged while incrementing $n$ to $n+1$. Constructors introducing no binders leave both counters unchanged:

\begin{lstlisting}[language=Lean4]
def Proc.lc : Nat -> Nat -> Proc -> Prop
  | _, _, .nil         => True
  | k, n, .one x P     => x.lc k '$\land$' P.lc k n
  | k, n, .tensor x P  => x.lc k '$\land$' P.lc (k + 1) n
  | k, n, .cut P       => P.lc (k + 2) n
  | k, n, .input x P   => x.lc k '$\land$' P.lc k (n + 1)
  | ...
\end{lstlisting}

A process is considered globally \emph{closed} when it contains no dangling indices of either sort, meaning \texttt{Proc.lc 0 0} holds. This is registered as the abbreviation \texttt{Proc.lc\_0}.

\paragraph{Free names} \path{Processes/Names.lean} defines 
\texttt{Proc.f~: Proc $\to$ Finset FPName} to compute the free channel names of a process. The function traverses the syntax tree structurally, collecting all explicit free channel identifiers into a finite set. Because locally nameless binders are represented using anonymous indices, bound channels contribute nothing to this set.

For constructors carrying explicit subject channels, such as \texttt{tensor} and \texttt{link}, the free names of those channels are combined with the recursively computed free names of their continuations. Constructors without explicit channel identifiers of their own, such as \texttt{cut}, contribute only the free names recursively obtained from their continuations:


\begin{lstlisting}[language=Lean4]
def Proc.f : Proc -> Finset FPName
  | .cut P      => P.f
  | .par P Q    => P.f '$\cup$' Q.f
  | .link x y   => x.f '$\cup$' y.f
  | .tensor x P => x.f '$\cup$' P.f
  | .one x P    => x.f '$\cup$' P.f
  | .nil        => {}
  | ...
\end{lstlisting}

\paragraph{Freshness} \path{Processes/Fresh.lean} establishes freshness to support the generation of globally unique names. Given a finite set $L$ of forbidden names, a strictly fresh name is deterministically computed as $\max(L) + 1$. The formalisation provides two critical lemmas, \texttt{exists\_one\_fresh} and \texttt{exists\_two\_fresh}, which guarantee the generation of one or two distinct names residing entirely outside of $L$. These lemmas are essential for providing witnesses to satisfy the co-finite quantification premises used throughout the typing and transition rules, particularly for restriction, which requires introducing two fresh, non-colliding endpoints simultaneously.

\paragraph{Name substitution} \path{Processes/SubstNames.lean} establishes the machinery for name substitution as \texttt{Proc.substNames (R T~: FPName)~: Proc $\to$ Proc}, replacing all explicit free occurrences of the target name $T$ with the replacement name $R$. Because the locally nameless architecture strictly partitions free names and bound indices into disjoint syntactic categories, substituting a free name $R$ only interacts with other explicit free names at the leaves of the syntax tree. Binders, which operate exclusively via relative De Bruijn indices, are fundamentally blind to the concrete name $R$. Therefore, this operation is intrinsically capture-avoiding by construction, completely eliminating the need for complex freshness constraints or $\alpha$-renaming during substitution.

\paragraph{Type substitution} \path{Processes/SubstTypes.lean} establishes the machinery needed for type substitution as \texttt{Proc.substTypes (A~: Types) (k~: Nat)~: Proc $\to$ Proc}, eagerly substituting $A$ for the De Bruijn index $k$ throughout a process. Because the syntax is two-sorted, the operation delegates to the type-level substitution machinery whenever it encounters an embedded type. For example, within an \texttt{output} prefix, \texttt{Types.subst} is applied directly to the transmitted type. When traversing an \texttt{input} prefix, which binds a type variable, the substitution descends with an incremented depth $k + 1$. Simultaneously, $A$ is explicitly shifted (\texttt{A.shift 0 1}) to prevent its free variables from being captured by the newly entered binder, mirroring the pattern used in \texttt{Types.subst} from \cref{subsubsec:stypes}:

\begin{lstlisting}[language=Lean4]
def Proc.substTypes (A : Types) (k : Nat) : Proc -> Proc
  | .input x P => .input x (P.substTypes (A.shift 0 1) (k + 1))
\end{lstlisting}

A consequence of the locally nameless representation is that no channel shifting operation (e.g. \texttt{shiftNames}) is required. In a pure De Bruijn encoding such as that used for \texttt{Types} in \cref{subsubsec:stypes}, variables are represented as relative indices and must be shifted when traversing binders to preserve correct binding structure. By contrast, free channels (\texttt{FPName}) are represented as global identifiers rather than relative positions, and are therefore unaffected by binder depth. This avoids the need for structural adjustment of channel names during substitution, simplifying the process-level infrastructure.

\paragraph{Structural Properties} \path{Processes/Lemmas.lean} establishes the fundamental structural properties required by the later typing and operational metatheory. This includes commutation lemmas for interacting operations (e.g., \texttt{open\_substNames\_comm}, showing that opening commutes with name substitution), preservation properties for local closure (e.g., \texttt{lc\_of\_open}), and lemmas relating binders to free-name analysis (e.g., \texttt{f\_close}, proving that closing removes a free name from the resulting term).

These results provide the core infrastructure required for the typing and transition semantics developed in subsequent chapters.

For completeness, the full inductive definition of \texttt{Proc} and all lemmas from \path{Processes/Lemmas.lean} are listed in \cref{app:processes}. % FIXME: Make an appendix for this.

\subsubsection{Environments}\label{subsubsec:environments}
Environments are defined in \path{Environment/Basic.lean} as 
\texttt{Env}, an abbreviation for a list of channel-type pairs:

\begin{lstlisting}[language=Lean4]
abbrev Elem := (FPName '$\times$' Types)
abbrev Env  := List Elem
\end{lstlisting}

The choice of \texttt{List} as the underlying representation deserves explanation, as it was not the first approach attempted. An initial implementation used \texttt{Finset} to directly model the unordered, duplicate-free nature of the theoretical environment. However, because \texttt{Finset} in Lean is implemented as a quotient type over lists, it inherently resists direct structural induction and pattern matching. This led to two distinct hurdles, namely the constant occurrence of dependent elimination failures, and the necessity of lifting functions and proofs reasoning about environments across the quotient equivalence. In the context of a process calculus, where inversion and structural manipulation of the typing context are omnipresent, this quotient infrastructure proved unwieldy. A second attempt using association lists (\texttt{AList}) encountered similar difficulties. The final design uses a plain \texttt{List} and recovers the unordered structure through an explicit permutation relation, trading quotient reasoning for structural induction, which interacts far more smoothly with Lean's tactic machinery.

\paragraph{Recovering the PCM structure} Merging two environments is implemented as list concatenation, making it a simple structural, but total, function:

%FIXME: Move together with other commands
\newcommand{\envmerge}[2]{#1,#2}
\newcommand{\perm}[2]{#1\sim#2} 
\newcommand{\hypermerge}[2]{#1\pp_h#2}


\begin{lstlisting}[language=Lean4]
abbrev Env.merge ('$\Gamma~\Delta$' : Env) : Env := '$\Gamma$' ++ '$\Delta$'
infixl:69 "'$,$'" => Env.merge
\end{lstlisting}

Because lists do not naturally form a Partial Commutative Monoid (PCM) but are associative by definition, we only need to formally recover commutativity. This is achieved by reasoning up to permutation equivalence, using Lean's built-in \texttt{List.Perm} relation, which is instantiated through a custom \texttt{HasPerm} typeclass and denoted by the infix relation \hl{$\thl{\Gamma \sim \Delta}$}. The essential monoidal laws are established as:

\begin{lstlisting}[language=Lean4]
lemma Env.merge_comm ('$\Gamma~\Delta$' : Env) : '$\perm{\envmerge{\Gamma}{\Delta}}{\envmerge{\Delta}{\Gamma}}$'
lemma Env.merge_assoc ('$\Gamma~\Delta~\Xi$' : Env) : '$\envmerge{\Gamma}{}\envmerge{\Delta}{\Xi}$' = '$\envmerge{\Gamma}{}$($\envmerge{\Delta}{\Xi}$)'

\end{lstlisting}

Additionally, we use \hl{$\thl{\emptyhyp}$} as unit for merging and implement identity for merging it on both the left and right side of an environment as well as some useful lemmas for defining a standard representation for example turning \hl{$\thl{e :: \emptyhyp}$ into $\thl{[e]}$}.

\begin{remark}
  \begin{highlight}  
    The use of $\thl{\emptyhyp}$ as unit has necessitated explicit lemmas to rewrite and reduce terms such as $\thl{\envmerge{\emptyhyp}{\Gamma} \text{ to } \Gamma}$. Whereas if $\thl{[]}$ were used as unit terms like $\thl{\envmerge{[]}{\Gamma}}$ would reduce by definitional equality, because the \texttt{Env.merge} notation is an abbreviation for \texttt{List.append}, Lean can see through it and reduce automatically.
  \end{highlight}
\end{remark}

The requirement that merging is only valid for disjoint environments, is partiality enforced via explicit predicates rather than a partial function. \texttt{Env.names} extracts the domain as a \texttt{Finset}, enabling Lean's built-in \texttt{Disjoint} typeclass. Internal linearity (no channel typed twice) is enforced by \texttt{Env.Nodup} (using List.Nodup as the underlying structure):

\begin{lstlisting}[language=Lean4]
def Env.names ('$\Gamma$' : Env) : Finset FPName := ('$\Gamma$'.map Prod.fst).toFinset 
def Env.disjoint ('$\Gamma~\Delta$' : Env) : Prop := Disjoint '$\Gamma$'.names '$\Delta$'.names
def Env.Nodup ('$\Gamma$' : Env) : Prop := ('$\Gamma$'.map Prod.fst).Nodup
\end{lstlisting}

The interaction between these predicates and merging is captured by \texttt{Env.Nodup\_merge\_iff}, which states that a merged environment is linear if and only if both components are linear and mutually disjoint.

\paragraph{Server usability} The typing rule for server replication requires all dependency channels to carry exponential types. Since Lean inductive constructors cannot explicitly express an arbitrary list of type constraints, this is abstracted into the \texttt{Env.serverUsable} predicate. This asserts that every type in a given environment satisfies \texttt{Types.isServerUsable}, a type-level predicate checking whether a type takes the form of an exponential request (\hl{$\thl{\query B}$}).

\begin{lstlisting}[language=Lean4]
def Env.serverUsable ('$\Gamma$' : Env) : Prop :=
  '$\forall$' p, p '$\in$' '$\Gamma$' -> p.snd.isServerUsable
prefix:max "?'$_e$'" => Env.serverUsable
\end{lstlisting}

\paragraph{Lifted operations} Since environments contain types, all locally nameless operations from \cref{subsubsec:stypes} are lifted pointwise over the type component of each \texttt{Elem}. Local closure, type shifting, name substitution, and type substitution are all defined by mapping over the list, and \path{Environment/Lemmas.lean} proves that each operation preserves the names, disjointness, nodup, and permutation properties of the environment.

The full definitions and lemmas are listed in \cref{app:environments}. %FIXME: make and references appendix

\subsubsection{Hyperenvironments}\label{subsubsec:hyperenvironments} Hyperenvironments are defined in \path{HyperEnvironment/Basic.lean} as \texttt{HyperEnv}, an abbreviation for a list of environments:

\begin{lstlisting}[language=Lean4]
abbrev HyperEnv := List Env
\end{lstlisting}

Merging is again list concatenation, using \hl{$\thl{\emptyhyp{}}$} as unit and $\hypermerge{}{}$ as merge operator to avoid clashing with Lean's built-in \emph{|}, with the unit and associativity laws holding definitionally, mirroring the environment design. However, recovering the commutative structure required a more extensive permutation relation than the one used for environments.

\paragraph{Deep permutation} For environments, \texttt{List.Perm} sufficed, as it allowed arbitrary reordering of elements. For hyperenvironments this is not enough. A hyperenvironment is a list of environments, so not only should reordering of the environments be allowed, but the environments themselves should also be permutation-equivalent. 

\begin{example}
  \begin{highlight}
    Consider the hyperenvironment $\thl{[\cht{x}{A}, \cht{y}{B}]}$, consisting of a single environment with two channel-type pairs. Under \texttt{List.Perm}, this would \emph{not} be equivalent to $\thl{[\cht{y}{B}, \cht{x}{A}]}$, since the single environment element is treated as an opaque value. Under \texttt{HyperEnv.Perm}, the \texttt{cons} constructor permits the head environment to be replaced by any permutation-equivalent environment, so $\thl{[\cht{x}{A}, \cht{y}{B}] \sim [\cht{y}{B}, \cht{x}{A}]}$ holds via \texttt{cons} with the environment permutation $\thl{\cht{x}{A}, \cht{y}{B} \sim \cht{y}{B},\cht{x}{A}}$.
  \end{highlight}
\end{example}

Standard \texttt{List.Perm} is a \emph{shallow} permutation implementation, meaning that it does not capture this. Here each environment is treated as an opaque element and cannot be permute. To address this, a custom \texttt{HyperEnv.Perm} inductive is defined:

\begin{lstlisting}[language=Lean4] 
inductive HyperEnv.Perm : HyperEnv -> HyperEnv -> Prop where
  | nil  : Perm [] []
  | cons : {'$\Gamma~\Delta$' : Env} {'$\hyp{G~H}$' : HyperEnv} : '$\perm{\Gamma}{\Delta}$' -> Perm '$\hyp{G}~\hyp{H}$' -> Perm ('$\Gamma :: \hyp{G}$') ('$\Delta :: \hyp{H}$')
  | swap : {'$\Gamma~\Delta$' : Env} {'$\hyp{G}$' : HyperEnv} : Perm ('$\Gamma :: \Delta :: \hyp{G}$') ('$\Delta :: \Gamma :: \hyp{G}$')
  | trans {'$\hyp{G~H~J}$' : HyperEnv} : Perm '$\hyp{G~H}$' -> Perm '$\hyp{H~J}$' -> Perm '$\hyp{G~J}$'
\end{lstlisting}

The \texttt{cons} constructor is the key distinction from \texttt{List.Perm}. Rather than requiring the head elements to be identical, it requires them to be \emph{environment-permutation-equivalent} (\hl{$\thl{\Gamma \sim \Delta}$}). This makes \texttt{HyperEnv.Perm} a \emph{deep} permutation implementation that propagates equivalence down to it elements as well as its own ordering. The remaining constructors mirror \texttt{List.Perm} directly.

\paragraph{Well-formedness} Hyperenvironments carry two distinct linearity conditions. \texttt{HyperEnv.Nodup} differs from \texttt{Env.Nodup}, by only requiring that each component environment is internally linear (no channel typed twice within a single environment), while ensuring that merging only occurs for disjoint environments is handled by \texttt{HyperEnv.PairwiseDisjoint}, which requires that the component environments are mutually disjoint, which ensures that no channel appears in two distinct components:

\begin{lstlisting}[language=Lean4]
def HyperEnv.Nodup ('$\hyp{G}$' : HyperEnv) : Prop :=
  '$\forall~\Gamma, ~\Gamma \in \hyp{G}$' -> Env.Nodup '$\Gamma$'

def HyperEnv.PairwiseDisjoint ('$\hyp{G}$' : HyperEnv) : Prop :=
  List.Pairwise Env.disjoint '$\hyp{G}$'
\end{lstlisting}

\begin{example}
  \begin{highlight}
    To illustrate this distinction, consider three candidate hyperenvironments under a naming context where $x, y, z$ are distinct channel names:
    \begin{itemize}
      \item \textbf{Well-formed:} $\thl{\hyp{G}_1 = \hypermerge{[\cht{x}{A}]}{[\cht{y}{B}, \cht{z}{C}]}}$ satisfies both predicates. Each component list has no duplicate channels, and their domains share no common names.
      \item \textbf{Fails \texttt{Nodup}:} $\thl{\hyp{G}_2 = \hypermerge{[\cht{x}{A}, \cht{x}{B}]}{[\cht{y}{C}]}}$ 
      satisfies \texttt{PairwiseDisjoint} because the two components do not share names, but it violates \texttt{Nodup} because the first environment has multiple occurences of $x$.
      \item \textbf{Fails \texttt{PairwiseDisjoint}:} $\thl{\hyp{G}_3 = \hypermerge{[\cht{x}{A}]}{[\cht{x}{B}, \cht{y}{C}]}}$ satisfies \texttt{Nodup} because both component environments are internally valid, but it violates \texttt{PairwiseDisjoint} because the channel $x$ crosses the parallel composition boundary and appears in both components.
    \end{itemize}
  \end{highlight}
\end{example}

Together these two predicates enforce the global linearity of a 
hyperenvironment, namely that every channel appears at most once across all components.

\paragraph{Lifted operations} As with environments, type shifting, name substitution, and type substitution are all lifted pointwise by mapping over the list of component environments.~\path{HyperEnvironment/Lemmas/Basic.lean} proves that each operation preserves names, disjointness, pairwise disjointness, and the deep permutation relation. The preservation of permutation under shifting is a representative example, it proceeds by induction on \texttt{HyperEnv.Perm}, using the corresponding environment-level lemma at the \texttt{cons} case. The full definitions and lemmas are listed in \cref{app:hyperenvironments}.

\subsubsection{Typing Judgements}\label{subsubsec:judgements}
The typing relation is defined in \path{Judgement/Basic.lean} as the inductive predicate \texttt{Typing}:

\begin{lstlisting}[language=Lean4]
inductive Typing : Nat -> Proc -> HyperEnv -> Prop
\end{lstlisting}

In informal notation this is written \hl{$\judge{n}{P}{\hyp{G}}$}. The natural number $n$ tracks the current type binder depth, as established in \cref{subsubsec:processes}. Whenever the derivation descends into a \texttt{forall\_} constructor, $n$ is incremented and the environment is shifted by one to keep all embedded type indices in scope:

\begin{lstlisting}[language=Lean4]
| forall_ {'$\Gamma$' : Env} {P : Proc} {x : FPName} {B : Types} {n : Nat} :
    Typing (n + 1) P [x : B :: '$\Gamma^{+t}$'] ->
    Typing n (#x'$\dparenL$'$T'$\dparenR$'.P) [x : '$\forall$'.B :: '$\Gamma$']
\end{lstlisting}

The shift \texttt{$\thl{\typeshift{\Gamma}}$} applied to the environment ensures that all free type indices in \hl{$\thl{\Gamma}$} are incremented to account for the newly introduced binder, mirroring the shift applied during type substitution in \cref{subsubsec:stypes}.

\paragraph{Exchange rules}
Rather than building commutativity into every constructor, the typing relation includes two explicit structural rules that allow reasoning up to permutation equivalence:

\begin{lstlisting}[language=Lean4]
| exchange_env   : Typing n P ('$\Gamma$' :: '$\hyp{G}$') -> '$\perm{\Gamma}{\Delta}$' -> Typing n P ('$\Delta$' :: '$\hyp{G}$')
| exchange_hyper : Typing n P '$\hyp{G}$' -> '$\perm{\hyp{G}}{\hyp{H}}$' -> Typing n P '$\hyp{H}$'
\end{lstlisting}

\texttt{exchange\_env} allows replacing a component environment with any permutation-equivalent one, while \texttt{exchange\_hyper} allows replacing the entire hyperenvironment. Together these recover the unordered character of the theoretical presentation from \cref{subsubsec:environments} without requiring a quotient type.

\paragraph{Co-finite quantification}
Binding constructors use co-finite quantification as described in \cref{subsec:co-finite-quantification}. For example, the \texttt{cut} constructor introduces two fresh dual endpoints:

\begin{lstlisting}[language=Lean4]
| cut {'$\hyp{G}$' : HyperEnv} {'$\Gamma~\Delta$' : Env} {P : Proc} {A : Types} {n : Nat} (L : Finset FPName) :
    '$\forall$' x '$\notin$' L, '$\forall$' y '$\notin$' L, x '$\neq$' y -> Typing n ('$\dopen{P}{\#x, \#y}$') ('$\hypermerge{G}{\hypermerge{[\cht{x}{A} :: \Gamma]}{[\cht{y}{\dual{A}} :: \Delta]}}$') ->
    Typing n ('$\dres{P}$') ('$\hypermerge{\hyp{G}}{[\Gamma, \Delta]}$')

\end{lstlisting}
The premise holds for any two distinct names $x, y$ outside the finite set $L$. This design serves two complementary purposes. When \emph{constructing} a typing derivation, the prover chooses $L$ to be large enough that any witness outside it is guaranteed fresh, typically the union of all free names currently in scope, and then uses \texttt{exists\_two\_fresh} to produce concrete witnesses. When \emph{using} a typing derivation, for example during inversion or induction, the universal quantifier allows the prover to instantiate $x$ and $y$ as whatever fresh names the current proof goal requires, rather than being tied to the specific names chosen during construction.

\paragraph{Structural invariants} The file \path{Judgement/Names.lean} establishes the key invariant \texttt{Typing\_f\_eq\_names}. That is for any well-typed process, the free names of the process are exactly equal to the domain of the hyperenvironment:

\[
n \vdash P \colon \hyp{G} \implies \texttt{Proc.f}~P = \texttt{HyperEnv.names}~\hyp{G}
\]

This ensures both that the process has no untyped free channels and that the environment contains no unused channels, strict linearity in both directions.

Building on this, \path{Judgement/Linearity.lean} proves \texttt{Typing\_preserves\_disjointness}: any well-typed hyperenvironment is pairwise disjoint. Together these two results guarantee that typing derivations can only be constructed for well-formed, linear contexts.

\paragraph{Type weakening}
\path{Judgement/Weakening.lean} establishes that typing is stable under type-level index shifting:
% FIXME: Notation used here should probably mirror the implementation notation instead of what looks nice
\[
n \vdash P \colon \hyp{G} \implies \forall d~c,\quad n + c \vdash P{\uparrow^t_{d,c}} \colon \hyp{G}{\uparrow^t_{d,c}}
\]

This is used whenever a process is placed under a new type binder, the existing derivation can be lifted to the new depth by shifting both the process and its hyperenvironment. The proof proceeds by structural induction on the typing derivation, with the \texttt{forall\_} case requiring careful composition of the shift operations.

\paragraph{Example derivation}
The \texttt{ax} constructor types the forwarding process $\phl{\forward{x}{y}}$, which links two dual endpoints directly:

\begin{lstlisting}[language=Lean4]
| ax {x y : FPName} {A : Types} {n : Nat} (hneq : x '$\neq$' y) :
    A.lc n ->
    Typing n ('$\plink{\#x}{\#2}$') [x : A'$^\bot$' :: [y : A]]
\end{lstlisting}

This requires only that $x \neq y$ and that the type $\thl{A}$ is locally closed at depth $n$. It produces a single-component hyperenvironment containing exactly the two endpoints with dual types, directly reflecting the axiom rule from \cref{fig:pill-typing-rules}. As the simplest typing derivation in the system, it also serves as the base case in inductive proofs over the typing relation.

The full inductive definition of \texttt{Typing} is listed in 
\cref{app:judgements}.
